依赖方向与接口落地

四张卡：模块角色 → 方向规则 → 验证命令 → 说法模板。面试前 5 分钟看这一页就够。

1 · 四个模块各自是什么

模块角色允许依赖判据
model领域实体 + 仓储接口谁都不依赖叶子；零外部依赖
common配置 / 日志 / JWT / metrics 底座谁都不依赖叶子；与 model 互不依赖
core外部系统驱动（PG / Redis / RabbitMQ / Supabase / 推送）common model只碰驱动，不碰业务分发
app业务用例 + delivery（HTTP/gRPC/WS/worker）+ 仓储实现 + 装配common core model唯一可执行模块

工作区由 go.work 编排（use ./common ./core ./model ./app），根目录不是 module，所以 go build ./... 失效，要用 go build all 或 go -C <模块>。

2 · 方向规则（一句话 + 一个反直觉点）

Dependency Rule 源码依赖只能指向内层、指向更稳定的一侧。出处：《Clean Architecture》第 22 章 InformIT 官方节选 · 作者原文

反直觉点：控制流是向外的（请求 app → usecase → repo 接口 → Redis 实现），但源码依赖是向内的（app/internal/repository/redis 里写的是 import "model/repository"）。两者方向相反，这个「相反」就是依赖倒置本身——不是命名游戏。

3 · 验证命令（自己跑，别信任何人转述）

# 秒级粗筛：内层不得出现外层 import 路径
cd my_go_study
grep -rl '"app/' core --include='*.go' | wc -l     # 期望 0
grep -rl '"common/\|"core/\|"app/' model --include='*.go' | wc -l   # 期望 0
grep -rl '"core/\|"model/' app --include='*.go' | wc -l             # 期望 > 0（本仓库 144）
# 编译器视角（可选深挖）：解析整张模块图，本机网络受限时会长时间无输出
go -C core list -deps ./... | grep -E '^app(/|$)'   # 期望无输出
go -C app  list -deps ./... | grep -E '^(core|model)(/|$)' | head

2026-10-29 实测：本机 go -C core list -deps ./... 超过 8 分钟无输出（go env 本身 0.015s 返回，卡的不是 go 命令而是模块图解析）。所以以 grep 为准，网络正常时再用这条复核。

为什么 grep 也够用 Go 的 import 别名（grpcdelivery "app/internal/delivery/grpc"）改的是包名、不改路径字符串，所以按 "app/ 搜不会漏。grep 的漏洞只有：字符串出现在注释或字符串字面量里（误报，不是漏报）。

4 · 接口在 Go 里怎么落地（本仓库真实三件套）

位置文件写的是什么
内层声明model/repository/session_repository.gotype SessionRepository interface 4 个方法 + DeviceSession 结构体
外层实现app/internal/repository/redis/session_repo.gotype SessionRepository struct 同类型名，方法集覆盖接口；import "model/repository"
消费方app/internal/delivery/worker/handler.go字段写成 sessions repository.SessionRepository，只认接口不认 Redis
 
// 编译期断言：Go 接口是隐式满足的，所以惯用这一行把「实现了」变成编译约束
var _ repository.RealtimeEventRepository = (*RealtimeEventRepository)(nil)
// 见 app/internal/repository/redis/realtime_event_repo.go:86
// 注意 session_repo.go 目前没有这行——隐式满足不会报错，改名/漏方法要到被使用时才暴露

隐式满足与「接口越小抽象越强」：Effective Go · Interfaces；接口值内部表示与代价：Go: Under the Hood 4.2。

5 · 60 秒说法模板（背结构，不背词）

模板 「我们后端是 4 个 Go module，靠 go.work 编排。model 和 common 是叶子，谁都不依赖；core 只封装外部系统驱动；app 装业务和装配。规则是源码依赖只能向内。

最典型的例子是单设备登录：SessionRepository 接口在 model 里，Redis 实现在 app 里。所以控制流向外、源码依赖向内——这就是依赖倒置。好处很具体：换存储不动业务代码，worker 只持有接口，测试可以塞内存实现。

代价我也说：多一层间接、读代码要多跳一次定义，小项目上这套是过度设计；我们是因为 同进程双端口 + 多中间件 + 多业务域 才划算。」
