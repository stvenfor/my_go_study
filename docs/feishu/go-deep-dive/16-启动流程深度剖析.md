# 16 · 启动流程深度剖析：goroutine 拓扑、失败语义矩阵与优雅关闭

> 一句话定位：[03 篇](03-启动流程与依赖注入.md)回答「15 个阶段装了什么」，本篇回答「装完以后进程里有几条并发流、哪个依赖挂了会死、SIGTERM 之后每一毫秒发生什么」——全部以 api/worker 两个 main 的行号为证。

## 通俗理解：把进程当成一家商场

`main()` 像商场开业：先通电通水（连 PG/Redis），再按招商情况决定开哪些铺位（feature toggle），最后开门营业（HTTP/gRPC 阻塞）。但 03 篇只画了「装修清单」，没回答三个开业后才暴露的问题：

1. **店里有几条同时运转的传送带？** 每条在哪个 goroutine，谁卡住会连累全场？
2. **停水停电分别怎么办？** 有的直接闭店（exit 1），有的贴个告示继续营业（Warn 降级），有的悄悄换成手工操作（mock 回退）。
3. **打烊广播（SIGTERM）之后，顾客和员工按什么顺序离场？**

本篇就按这三问展开，外加条件分支时序、`/health` 真相和六个实战坑。

### 1.3 重要纠偏：本项目的 Hub 没有 Run 循环

gorilla/websocket 官方 chat 示例里 Hub 自带一个中央 `Run()` goroutine，靠 `register/unregister/broadcast` 三个 channel 串行化所有操作。本项目**不是这样**：

- [hub.go](file:///Users/qpy/Desktop/github/my_go_study/app/internal/delivery/ws/hub.go) 全文没有 Run、没有 channel 字段；`Hub` 只有一把 `sync.RWMutex` 和两个 map [L25-L33](file:///Users/qpy/Desktop/github/my_go_study/app/internal/delivery/ws/hub.go#L25-L33)。
- `Register` [L44-L58](file:///Users/qpy/Desktop/github/my_go_study/app/internal/delivery/ws/hub.go#L44-L58)、`Unregister` [L61-L78](file:///Users/qpy/Desktop/github/my_go_study/app/internal/delivery/ws/hub.go#L61-L78) 是**调用方 goroutine 直接持锁执行**的普通方法（分别由 WS 鉴权处理和 readPump 的 defer 调用）。
- 广播也不经过 Hub goroutine：`BroadcastToUser` 在 RLock 内复制连接列表、解锁后逐个 `c.Send` [L82-L100](file:///Users/qpy/Desktop/github/my_go_study/app/internal/delivery/ws/hub.go#L82-L100)；`Send` 只是非阻塞往容量 32 的 buffered channel 丢消息 [client.go L103-L109](file:///Users/qpy/Desktop/github/my_go_study/app/internal/delivery/ws/client.go#L103-L109)。

这意味着：广播风暴时 Hub 不会成为单 goroutine 瓶颈，但代价是**没有中央调度点，也就没有「Hub 关闭」这一步**——这个缺口在第三节会再次出现。

### 1.4 worker 进程 goroutine 拓扑

```text
worker main goroutine
├─ 串行装配：config（queue.enabled=false 直接退出）→ Redis → MQ Client → PG
├─ go A  consumer.Run(ctx, handler)   worker/main.go L118-L127
│        └─ for-select：ctx.Done() vs deliveries 通道  consumer.go L90-L105
├─ go B  RunHourlyNotifyTicker(ctx)   worker/main.go L129
│        └─ 1 分钟 ticker，整点命中 cron 才入队      hourly_ticker.go L30-L57
└─ <-quit → cancel() → return（不等 A/B 退出！）     worker/main.go L131-L137
```

ticker 自身还有开关：`scheduler.enabled` 或 `hourly_notify.enabled` 为 false 时，goroutine 进去打一条日志就返回，**不会创建 ticker** [hourly_ticker.go L19-L22](file:///Users/qpy/Desktop/github/my_go_study/core/queue/hourly_ticker.go#L19-L22)。dev 配置恰好关闭（[config.dev.yaml L38-L41](file:///Users/qpy/Desktop/github/my_go_study/configs/config.dev.yaml#L38-L41)），需要手动 `make trigger-hourly-notify`。

## 二、失败语义矩阵：谁致命、谁降级、谁偷偷回退

通俗讲：同样是「连不上」，PG 是心脏停跳必须死，ES 是老花眼戴不戴眼镜都能走路。代码里把失败处理分成了四个等级，先记住词表：

| 等级 | 代码形态 | 后果 |
|---|---|---|
| 启动中止 | `return err` → main 打印「启动失败」`os.Exit(1)` [main.go L69-L72](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L69-L72) | 进程退出，defer 会执行 |
| 运行期致命 | goroutine 内 `log.Fatal`（zap 内部 `os.Exit(1)`） | 进程立即退出，**defer 不执行** |
| 降级继续 | `log.Warn` 后跳过该能力 | 功能缺失，进程存活 |
| 默认回退 | 静默或 Warn 后换成 mock/默认值 | 功能「看起来可用」 |

## 三、优雅关闭全过程

通俗讲：HTTP Shutdown 是「停止接新客、等店内客人结账」，gRPC GracefulStop 是同义操作；但 WS 顾客是「翻墙进店」的（hijack），商场的打烊流程根本数不到他们——这是本篇最需要警惕的细节。

### 3.1 api 关闭时间线（逐行）

信号注册在所有 server 启动**之后**：`signal.Notify(quit, SIGINT, SIGTERM)` 然后 `<-quit` 阻塞 [main.go L573-L575](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L573-L575)。收到信号后：

| 顺序 | 动作 | 行号 | 超时/错误处理 |
|---|---|---|---|
| 1 | 建 10s 超时 ctx | [L578-L579](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L578-L579) | `defer cancel()` |
| 2 | gRPC `GracefulStop()`：不再接新 RPC，等在途 RPC 结束 | [L581-L584](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L581-L584)、[grpc/server.go L67-L72](file:///Users/qpy/Desktop/github/my_go_study/app/internal/delivery/grpc/server.go#L67-L72) | **无独立超时**，理论上可无限等 |
| 3 | RabbitMQ `queueClient.Close()`：先关 channel 再关 conn | [L586-L590](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L586-L590)、[client.go L41-L57](file:///Users/qpy/Desktop/github/my_go_study/core/queue/client.go#L41-L57) | 失败只 Warn |
| 4 | HTTP `server.Shutdown(ctx)`：关 listener、等在途普通 HTTP 请求 | [L592-L595](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L592-L595) | 超 10s 返回错误 → run return 非 nil → 进程 exit 1 |
| 5 | run 返回，defer 按 LIFO 执行：Redis Close → sqlDB Close → logger.Sync | 注册点 [L90](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L90)、[L105](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L105)、[L115-L119](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L115-L119) | Redis 关闭失败 Warn |

三个设计要点：

1. **先关流量入口（gRPC），再关消息出口（MQ），最后关 HTTP**。MQ 在 HTTP 之前关闭，意味着 Shutdown 窗口期内新进来的 HTTP 请求若尝试入队会失败——代码接受这个窗口。
2. **HTTP server 只设了 `ReadHeaderTimeout: 10s`** [main.go L531-L535](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L531-L535)，没有 WriteTimeout/IdleTimeout——这是 SSE 长连接和 WS 的必要条件，但也意味着慢客户端不受写超时保护。
3. 若 Shutdown 返回错误，main 仍走 `os.Exit(1)` [L69-L72](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L69-L72)，defer 已执行完。

### 3.2 WebSocket 客户端在关闭时的真实命运

这是代码里最「裸」的一段，三步推导：

1. WS 升级后连接被 gorilla `Upgrade` **hijack**，不再受 `net/http` 连接状态机管理；Go 文档明确 `Server.Shutdown` 不等待 hijacked 连接。
2. 全仓没有 `Hub.Close()` 或任何「关闭时遍历连接发 Close 帧」的代码：Hub 无 Run 循环（见 1.3），关闭序列里也没有 WS 的位置。
3. Pub/Sub goroutine 启动时传的是 `context.Background()` [main.go L321](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L321)，**关闭序列没有任何 cancel 能通知它**；它实际靠第 5 步 defer 关掉 Redis 连接后，订阅通道报错退出。

所以 SIGTERM 后 WS 客户端的体验是：没有应用层 Close 帧，进程退出时 TCP 连接被内核关闭，客户端靠自己的心跳/重连机制发现断线。writePump 里「send 通道关闭则优雅发 Close 帧」的分支 [client.go L153-L157](file:///Users/qpy/Desktop/github/my_go_study/app/internal/delivery/ws/client.go#L153-L157) 只在 `Unregister` 主动 `close(client.send)` [hub.go L77](file:///Users/qpy/Desktop/github/my_go_study/app/internal/delivery/ws/hub.go#L77)（即 readPump 先死）时触发，打烊路径走不到。

### 3.3 worker 关闭序列与 in-flight 消息

worker 没有 HTTP，关闭动作只有一句 `cancel()` [worker main.go L134-L136](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/worker/main.go#L134-L136)，随后 run 返回，defer 按 LIFO 执行：`cancel()`（幂等）→ `consumer.Close()` → `queueClient.Close()` → sqlDB.Close → Redis Close。

in-flight 消息的确切语义，要对着消费循环看：

- 循环是 `select { case <-ctx.Done(): return; case d := <-deliveries: Dispatch(...) }` [consumer.go L90-L105](file:///Users/qpy/Desktop/github/my_go_study/core/queue/consumer.go#L90-L105)。`cancel()` **只能打断「等下一条」的阻塞**，不能打断已经进入 `Dispatch` 的消息。
- Dispatch 失败：`Nack(false, true)`——requeue=true，消息重回队列 [L98-L101](file:///Users/qpy/Desktop/github/my_go_study/core/queue/consumer.go#L98-L101)；成功：`Ack` [L103](file:///Users/qpy/Desktop/github/my_go_study/core/queue/consumer.go#L103)。Dispatch 拿到的正是被取消的 ctx [worker L124](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/worker/main.go#L124)，下游 Redis/DB 操作可能因此失败转 Nack。
- **主 goroutine 没有 WaitGroup，不等待消费 goroutine 退出**就开始 defer 关 channel/conn。此时若一条消息既没 Ack 也没 Nack，AMQP 连接被关后 broker 会自动把未确认消息重新入队——整体是「至少一次」语义，但存在「业务已执行完、Ack 前连接被关 → 重启后重复执行」的窗口。整点广播靠 Redis `SetNX` 幂等键兜底（[worker/handler.go L134-L143](file:///Users/qpy/Desktop/github/my_go_study/app/internal/delivery/worker/handler.go#L134-L143)），普通 Push 任务则依赖下游幂等。
- QoS prefetch 默认 10 [config.go L426-L431](file:///Users/qpy/Desktop/github/my_go_study/common/config/config.go#L426-L431)，即单 worker 最多 10 条未确认消息，重放窗口上限就是 10。

## 六、坑与边界清单

1. **启动顺序的隐含耦合**：gRPC 必须有 Authenticator，Authenticator 必须有 deviceSessionUC（Redis 会话）+ 认证后端 [main.go L545-L570](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L545-L570)；membership 依赖 payment、mall 依赖 access/points/wallet，这些顺序靠 main.go 手工排列，调换代码块顺序会 nil 注入。
2. **HTTP 端口占用是异步暴露的**：gRPC 的 `net.Listen` 在装配期同步失败（return err），HTTP 的 bind 失败发生在 goroutine 里，表现为主流程继续走到「等信号」、随后 goroutine `log.Fatal`，且 `log.Fatal` 直接 exit，defer 的 PG/Redis 关闭不执行。调试「启动日志一切正常却立刻退出」要查这条。
3. **dev 默认 `queue.enabled: true`**（[config.dev.yaml L29](file:///Users/qpy/Desktop/github/my_go_study/configs/config.dev.yaml#L29)）：本机没起 RabbitMQ 时，`make run` 的 api 会在装配期 [L308-L311](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L308-L311) 直接退出；不想跑 MQ 要显式 `QUEUE_ENABLED=false`。
4. **Docker 里代码和 configs 都是构建期打入的**：二进制在 build 阶段编译 [Dockerfile L42-L43](file:///Users/qpy/Desktop/github/my_go_study/docker/Dockerfile#L42-L43)，configs 也是 `COPY` 进镜像 [Dockerfile L59](file:///Users/qpy/Desktop/github/my_go_study/docker/Dockerfile#L59)，compose 只挂载了 logs 目录 [docker-compose.yml L112-L113](file:///Users/qpy/Desktop/github/my_go_study/docker/docker-compose.yml#L112-L113)。改 Go 代码或改 yaml 都必须重新 build 镜像；想不改镜像调配置，只能走环境变量覆盖（清单见 [config.go L646-L717](file:///Users/qpy/Desktop/github/my_go_study/common/config/config.go#L646-L717)）。
5. **端口表**：HTTP/WS 共用 8080；gRPC 9090（`EXPOSE 8080 9090` [Dockerfile L63](file:///Users/qpy/Desktop/github/my_go_study/docker/Dockerfile#L63)）；宿主机上 Prometheus 占 9091→容器 9090、Alertmanager 9093、RabbitMQ 管理台 15672、Grafana 3000（[docker-compose.yml L34-L36](file:///Users/qpy/Desktop/github/my_go_study/docker/docker-compose.yml#L34-L36)、[L171-L172](file:///Users/qpy/Desktop/github/my_go_study/docker/docker-compose.yml#L171-L172)）。9090 被占时 gRPC 同步报错，9091 被占只影响 Prometheus。
6. **WS 无打烊流程**（见 3.2）：生产上发版重启时，在线 WS 客户端不会收到 Close 帧；客户端必须有重连逻辑。另外 upgrader 的 `CheckOrigin` 恒为 true [ws/handler.go L35-L37](file:///Users/qpy/Desktop/github/my_go_study/app/internal/delivery/ws/handler.go#L35-L37)，注释自述生产应收紧域名。
7. **Pub/Sub goroutine 不可取消**：`context.Background()` 启动 [main.go L321](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L321)，关闭时存在「Redis 已不打算用、订阅 goroutine 还在跑」的短暂泄漏窗口，靠 defer 关连接被动收尾；关闭过程中它若收到消息仍会向正在解散的 Hub 广播。
8. **worker 关停机不等待在途消息**（见 3.3）：滚动更新 worker 时最多 10 条（prefetch）消息可能被重放，业务 handler 需自行幂等；广播任务有 SetNX 幂等，普通 Push 任务无去重。
9. **`/health` 假象**：它通过不代表任何依赖可用；依赖断连多发生在运行期（Redis 断了不会让 api 退出，只是相关请求报错），不要用它做依赖告警，应配合 `/metrics` 与外部探测。
10. **种子失败只 Warn 的双刃性**：启动更健壮，但「商城没商品、社区没话题」可能只是一条被淹没的 Warn 日志；排查环境数据缺失先 grep `种子` / `准备失败`。

## 学习要点回顾

1. 主 goroutine 只做装配与等信号，HTTP、gRPC、Pub/Sub、WS pump 全在子 goroutine；数 goroutine 要按「每 WS 连接 +2」计算。
2. 本项目 Hub 是「RWMutex + buffered channel」的无中央循环设计，没有 Run 也没有 Close——性能选择的代价是关闭流程覆盖不到 WS。
3. 失败语义分四级：启动 return、goroutine log.Fatal（defer 不执行）、Warn 降级、mock/默认回退；PG/Redis/JWT secret 是硬依赖，ES/JPush/融云/SSE key 都是软依赖。
4. Supabase 客户端构造期不探活，ES 只做搜索旁路不改主仓储——「接口能返回」和「外部服务真的通」在这套代码里是两件事。
5. 优雅关闭顺序固定为 gRPC→MQ→HTTP(10s)→defer 关 Redis/PG；gRPC 无独立超时，WS 完全不在 Shutdown 管辖内。
6. worker 的 SIGTERM 只 cancel 等待中的 select，在途消息靠 broker requeue 实现至少一次，幂等由业务侧 SetNX 等手段保证。
7. 功能开关最终都物化成「nil 指针 + 注册前判空」：控制器 nil 不挂路由、Service nil 不入 DomainRouters，且 router.Setup 会二次校验。
8. `/health` 是进程存活信号而非依赖探针；真正的依赖健康信息只零散体现在日志和 `/metrics` 计数器里。
9. Docker 镜像构建期编译代码并拷入 configs，运行时只挂 logs——改代码/配置忘 rebuild 是最常见的「我改了怎么没生效」。
