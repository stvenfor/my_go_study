# 14-可观测性与外部集成

> 一句话定位：本文讲清两件「楼外的事」——一是 BFF 怎么用 Prometheus 把自己的健康状况（QPS、延迟、5xx、ES 失败）报出去，二是两类外部服务（极光 JPush 离线推送、融云 RongCloud IM）怎么从裸 HTTP 客户端一路接到路由。所属模块：common/metrics、app（middleware、core 适配层、usecase、controller、repository/postgres）、core/jpush、core/rongcloud、deploy/observability。阅读前置：[04-HTTP路由与中间件](04-HTTP路由与中间件.md)（路由链与统一信封）、[05-认证与会话](05-认证与会话.md)（会话身份与 user_id 来源）。

## 通俗理解

- **Prometheus** 是楼里的「自动抄表员」：每个请求结束，中间件往三个计数器/秒表里记一笔（多少次、多慢、什么状态段），`/metrics` 是抄表口，Prometheus 每 15 秒来抄一次；Grafana 把数字画成图，Alertmanager 在 5xx 超 5%、P99 超 2 秒、目标掉线时通过飞书机器人喊人。
- **JPush（极光）** 是「短信代发员」：App 启动时把极光 RegistrationID 报到 `wys_push_devices` 表；WS 在线推送发完后，服务端再调极光 REST v3 补一条系统通知（deeplink 放在 extras 里），别名默认就是业务 user_id。
- **融云** 是「外包的电话局」：消息通道本身是 App ↔ 融云 SDK 直连，BFF 不转发消息；BFF 只做四件事——签发连接 token、管好友关系与单聊准入（本地库）、管群（调融云群 API + 本地镜像）、接收客户端上报的消息做业务备份。
- **设计共性**：两个外部服务都没有官方 Go SDK，core 层用标准库 net/http 手写薄客户端（10 秒超时、响应体限 1MB、凭证缺失时构造不报错、调用时返回 ErrNotConfigured）；usecase 通过接口持有 core 客户端，可替换假实现做单测。

源码主锚点：`common/metrics/metrics.go`、`app/internal/delivery/http/middleware/prometheus.go`、`core/jpush/client.go`、`core/rongcloud/client.go`、`app/internal/usecase/{jpush,im_session,im_friend,im_group,im_backup}_usecase.go`、`app/internal/delivery/http/controller/{jpush,im}_controller.go`、`app/internal/repository/postgres/{push_device_repo,im_repo}.go`、`app/internal/repository/postgres/sql/{push_device,im}_schema.sql`、`deploy/observability/`、`docs/observability-lan.md`。

## 1. 全景装配

- 指标：进程级独立 Registry（`metrics.Registry`），`init()` 注册 Go runtime、process 采集器与 3 个业务指标；`router.Setup` 挂全局中间件 `middleware.PrometheusHTTP()` 与裸路由 `GET /metrics`（见 [04](04-HTTP路由与中间件.md) §1）。
- 极光：main.go（api 与 worker 两个入口）构造 `jpush.Client → PushDeviceRepository → JPushUsecase → JPushController`，并在 `app/cmd/api/main.go:387` 与 `app/cmd/worker/main.go:100` 调 `pushUC.SetOfflinePusher(jpushUC)` 注入 WS 离线兜底。
- 融云：`rongcloud.Client → ImSessionUsecase/ImGroupUsecase`，加 `ImFriendRepository/ImUserLookupRepository/ImBackupRepository` 组成 `ImSession/ImFriend/ImGroup/ImBackup` 四个 usecase，聚合进一个 `ImController`，挂 `/api/v1/im` 15 条路由（全表见 [04](04-HTTP路由与中间件.md) §2.6）。
- 建表：`EnsurePushDeviceSchema(db)` 与 `EnsureImSchema(db)` 都是「执行内嵌 `CREATE TABLE IF NOT EXISTS` SQL + GORM AutoMigrate」双保险，幂等可重复执行。

## 2. Prometheus 可观测性

### 2.1 指标登记表（`common/metrics/metrics.go`）

进程用的是**自建 Registry**（`prometheus.NewRegistry()`，L13），不是默认全局 registry；`init()`（L39-L47）一次性注册：

| 注册项 | 类型 | 名字 / 标签 | 含义 |
| --- | --- | --- | --- |
| `collectors.NewGoCollector()` | Go runtime 采集器 | go_* / process_go_* 系列 | goroutine、GC、内存等 |
| `collectors.NewProcessCollector(...)` | 进程采集器 | process_* 系列 | CPU、FD、RSS 等 |
| `HTTPRequestsTotal` | CounterVec | `http_requests_total{method,route,status_class}` | 按 HTTP 方法、**路由模板**、状态段累计请求数 |
| `HTTPRequestDuration` | HistogramVec | `http_request_duration_seconds{method,route}` | 请求延迟（秒）；桶：.005,.01,.025,.05,.1,.25,.5,1,2.5,5,10 |
| `ESTransactionIndexFailures` | Counter | `es_transaction_index_failures_total` | 收支记录 ES 索引/删除的尽力而为失败次数 |

辅助函数/导出：

| 声明 | 职责 | 备注 |
| --- | --- | --- |
| `Handler() http.Handler` | 文本格式 exposition 口 | `promhttp.HandlerFor(Registry, {EnableOpenMetrics:false})` |
| `StatusClass(code)` | 状态码归并 | <200→1xx、<300→2xx、<400→3xx、<500→4xx、其余 5xx |

`ESTransactionIndexFailures` 的唯二打点处：`app/internal/transaction/service.go:98`（Index 失败）与 `:110`（Delete 失败），均在 best-effort 路径——ES 写失败只计数+Warn 日志，不影响 PG 主链路。

### 2.2 采集中间件（`middleware/prometheus.go`）

`PrometheusHTTP()` 全文 31 行，函数级行为：

| 步骤 | 行为 |
| --- | --- |
| 1 | 取真实 `URL.Path`，等于 `/metrics` 或 `/health` 直接 `c.Next()` 返回——**不计数**，避免健康检查与自抓取污染指标 |
| 2 | 记 start，`c.Next()` 放行全链 |
| 3 | route 取 `c.FullPath()`（Gin 注册模板，如 `/api/v1/wallet`）；空串（404 未匹配）记 `unmatched`——**低基数关键**：真实 URL 里的 user_id/order_id 不会进 label |
| 4 | `HTTPRequestsTotal.WithLabelValues(method, route, StatusClass(status)).Inc()` |
| 5 | `HTTPRequestDuration.WithLabelValues(method, route).Observe(耗时秒)` |

注意：指标在 `c.Next()` **之后**记录，因此拿到的是最终状态码；405（方法不允许）也会以 `unmatched` 或 Gin 内部模板计入。

### 2.3 抓取、告警与看板（`deploy/observability/` + `docs/observability-lan.md`）

`make lan-up` 拉起的栈（来源：observability-lan.md 表格）：

| 服务 | 容器内 | 本机访问 |
| --- | --- | --- |
| API metrics | `app:8080/metrics` | http://127.0.0.1:8080/metrics |
| Prometheus | :9090 | http://127.0.0.1:9091 |
| Alertmanager | :9093 | http://127.0.0.1:9093 |
| Grafana | :3000 | http://127.0.0.1:3000（admin/admin） |
| feishu-adapter | :8089（仅内网） | 无宿主机端口 |

`prometheus.yml`：scrape/evaluation 间隔均 15s，job=app、metrics_path=/metrics、target `app:8080`，label service=my_go_study_api；规则文件挂 alerts.yml，Alertmanager 指向 `alertmanager:9093`。

`alerts.yml` 三条规则：

| 告警 | PromQL 要点 | 持续 | 级别 |
| --- | --- | --- | --- |
| APIHigh5xxRate | 5xx 速率 / 全量速率（`clamp_min(...,0.001)` 防除零）> 0.05 | 2m | warning |
| APITargetDown | `up{job="app"} == 0` | 1m | critical |
| APIHighLatencyP99 | `histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le)) > 2` | 5m | warning |

告警去向：Alertmanager → `feishu_adapter.py` → 飞书群机器人（webhook 由 `FEISHU_ALERT_WEBHOOK_URL` 注入；未配置时 adapter 回 204 丢弃，compose 不失败）。安全边界：`/metrics` 在应用层**无鉴权**（router 注释明确「不经 SessionAuth，仅本机/内网可达」），暴露面靠 compose 网络隔离。

### 3.1 core 客户端函数表（`core/jpush/client.go`，179 行）

无官方 Go SDK，标准库 HTTP 直调 `https://api.jpush.cn/v3/push`。

| 声明 | 职责 | 关键行为/坑 |
| --- | --- | --- |
| `Config{AppKey,MasterSecret,PushURL,APNsProduction,HTTPClient}` | 凭证与开关 | `APNsProduction` 对应 options.apns_production（dev 通常 false） |
| `Config.Configured()` | 是否可发 | key/secret 非空 **且 AppKey 大写后不含 "PLACEHOLDER"**（占位值识别） |
| `Notification{Title,Alert,Deeplink,Extras,Platform,AudienceAlias,AudienceRegistrationIDs}` | 推送内容 | Platform 空=all（all/android/ios/hmos）；两种受众 |
| `Result{MsgID,SendNo,Raw}` | 响应摘要 | Raw 保留原始 map |
| `NewClient(cfg)` | 构造 | 未配置也能构造；HTTP client 默认 **10s 超时**；PushURL 空回落默认值 |
| `ErrNotConfigured` | 哨兵 | key/secret 缺失/占位 |
| `(*Client).Send(ctx, n)` | 发推送 | 见下方流程 |
| `basicAuth(appKey,secret)`（未导出） | `base64(appKey:masterSecret)` | 放 Authorization: Basic 头 |

Send 内部流程（L76-L174）：① nil/未配置→ErrNotConfigured；② 两类受众全空→`jpush audience empty`；③ Alert 空回退 Title，再空→`jpush alert empty`；④ extras 拷贝并补 `deeplink`；⑤ platform 空→all，audience 同时支持 alias 与 registration_id；⑥ 三端 payload：android（alert+可选 title+extras）、ios（alert={title,body}、sound=default、extras）、hmos；options 带 apns_production；⑦ POST JSON，Basic 认证，响应体 `LimitReader 1MB`；⑧ 非 2xx 返回带状态码与响应体的错误（成功也保留 Raw）；⑨ msg_id 兼容字符串与 float64（数字时格式化 %.0f）。

⚠️ 注意：CHECK 里保留了 `ohos` 但 normalizePlatform 永远不会写入 ohos（会被归一成 harmony）——约束比代码宽，不影响运行。

### 3.5 WS 离线兜底接线

`app/internal/usecase/realtime_push_usecase.go`：`OfflinePusher` 接口（L47-L49）就一个方法 `NotifyUser(...)`；`SetOfflinePusher` 在构造后注入（api、worker 两入口都注入同一个 JPushUsecase）。实际触发点 `realtime_push_usecase.go:155-169`：先 `hub.BroadcastToUser` 走 WS，随后**只要 offline 非 nil 就无条件调 NotifyUser**（从 extra 里提取 deeplink），错误用 `_, _ =` 吞掉。
⚠️ 代码注释称「离线通道（极光）；失败不阻断 WS 投递」，但实现并未按 `delivered` 判断是否离线——**在线用户也会同时收到一条极光通知**，是否去重完全靠客户端。

## 5. IM 四 usecase（业务层）

四 usecase 与端口关系：

| usecase | 持有端口 | core 客户端接口 |
| --- | --- | --- |
| ImSessionUsecase | `repository.ImUserLookup` | `RongCloudTokenClient{GetToken}` |
| ImFriendUsecase | `ImFriendRepository` + `ImUserLookup` | 无（好友关系纯本地） |
| ImGroupUsecase | `ImGroupRepository` | `RongCloudGroupClient{CreateGroup,JoinGroup,QuitGroup,DismissGroup}`（`*rongcloud.Client` 天然满足） |
| ImBackupUsecase | `ImBackupRepository` | 无 |

仓储端口定义在 `model/repository/im_repository.go`，哨兵：`ErrImFriendRequestNotFound`、`ErrImFreeGroupNotFound`、`ErrImFreeGroupDismissed`、`ErrImNotGroupOwner`、`ErrImNotGroupMember`。

### 5.1 ImSessionUsecase（连接凭证，`im_session_usecase.go`）

| 声明 | 职责 |
| --- | --- |
| `ImSessionOutput{UserID,Token,ExpiresInSeconds}` | 响应体；ExpiresInSeconds 固定 **0**——融云 token 默认永久，0=未声明 TTL |
| `ErrImNotConfigured` / `ErrImUserIDRequired` | 哨兵 |
| `IssueSession(ctx,userID,displayName)` | client nil→ErrImNotConfigured；userID trim 后空→ErrImUserIDRequired；查本地 users：昵称优先用入参 displayName，空则取 UserName；头像取 AvatarURL；调 `GetToken`，把 `rongcloud.ErrNotConfigured` 翻译成 ErrImNotConfigured |

### 5.2 ImFriendUsecase（好友与单聊准入，`im_friend_usecase.go`）

业务哨兵：`ErrImFriendSelf/Already/Pending/UserMissing/NotPeer`、`ErrImSearchQueryEmpty`。数据结构：好友申请单表（from→to + status），好友关系用**字典序双向单行**（user_a < user_b，DB 有 CHECK 兜底）。

| 方法 | 行为与坑 |
| --- | --- |
| `Search(ctx,selfID,q)` | q 空→ErrImSearchQueryEmpty；`looksLikeUUID`（uuid.Parse 成功）走 FindByUserID，否则 `digitsOnly` 抽数字走 FindByPhone；查无或查错都返回**空列表 + nil**（不向客户端暴露「不存在」之外的差异）；命中自己→空；返回带 `maskPhone`（前 3 + **** + 后 4，不足 7 位返回空） |
| `ListFriends(userID)` | ListFriendIDs 后**逐个 FindByUserID 补资料**（N+1 查询；查不到就只显示 ID） |
| `ListProfiles(userIDs)` | 批量 FindByUserIDs（去重在 repo 内）；昵称空回退 UUID |
| `Request(from,to)` | 校验：两端非空、不可加自己、to 必须存在、不可已是好友、`FindPending(from,to)` 无**同向** pending；通过则生成 UUID 申请单（status=pending，UTC 时间）。⚠️ 只查同向：B→A 的申请 pending 时 A 仍可再发一条，形成双向两条 pending |
| `ListIncoming(toUserID)` | 收件箱：status=pending、created_at DESC，逐条补申请人资料（N+1） |
| `Respond(actorID,requestID,accept)` | 先取单（不存在→repo 哨兵）；**只有收件人能处理**（ToUserID 不符→ErrImFriendNotPeer）；非 pending 状态幂等返回当前状态；accept：先 UpsertFriendship（ON CONFLICT DO NOTHING）再 UpdateRequestStatus=accepted；reject：只改状态。⚠️ 两步非事务：关系写成功但状态更新失败会留下「已是好友但申请仍 pending」 |
| `CanPrivateChat(a,b)` | 单聊准入：空参或 a==b→false；否则查是否好友。这是**给客户端调用的查询接口**（GET /private/admission），BFF 不拦截融云消息本身 |
| 工具 `looksLikeUUID/digitsOnly/maskPhone` | UUID 判定、手机号抽数字、脱敏 |

### 5.3 ImGroupUsecase（自由群 + 门店群，`im_group_usecase.go`）

群 ID 约定：自由群 `"free_"+UUID`；门店群 `"store_"+storeID`（确定性，一店一群）。

| 方法 | 权限/流程与坑 |
| --- | --- |
| `CreateFreeGroup(ownerID,name,memberIDs)` | owner/name 必填；成员=入参并上 owner 后 `uniqueIDs` 去重；**先调融云 CreateGroup，成功后本地事务写群+成员**；融云成功本地失败会留下融云侧孤儿群（错误照常返回，无补偿） |
| `InviteFreeGroup(actor,groupID,ids)` | `requireOwner`：群存在、未解散、actor==群主；ids 去重后非空；先融云 JoinGroup 再本地 AddFreeMembers（逐条 ON CONFLICT DO NOTHING，非事务） |
| `KickFreeGroup(actor,groupID,ids)` | 同上鉴权；踢人名单自动**跳过群主自己**；全被跳过→`no members to kick`；融云 QuitGroup + 本地删成员 |
| `QuitFreeGroup(actor,groupID)` | 成员主动退：群未解散、**群主不能退（必须解散）**、必须是成员（ErrImNotGroupMember）；融云 QuitGroup + 本地删行 |
| `DismissFreeGroup(actor,groupID)` | requireOwner 后融云 DismissGroup + 本地软解散（写 dismissed_at）。⚠️ 成员表行不清理 |
| `EnsureStoreMembership(storeID,userID)` | 实现 `shared.ImStoreGroupSyncer`（`app/internal/shared/im_sync.go`），供 **access 域（入店/离店）与 profile 域（切门店后补拉）**跨域消费；有本地映射则用存量 groupID，否则建群：融云 CreateGroup **失败被显式忽略**（注释：群可能已存在于融云）→ UpsertStoreGroup（store_id 冲突时更新 group_id/updated_at）→ 再 JoinGroup 拉人 |
| `RemoveStoreMembership(storeID,userID)` | 无本地群映射→**noop 返回 nil**；有则融云 QuitGroup（本地不动映射） |
| `requireOwner`（未导出） | not-ready 防御 + 群存在 + 未解散 + 群主校验 |
| `uniqueIDs`（未导出） | trim/去空/去重保序 |

## 6. 已知边界与风险清单（零杜撰）

1. **/push/send 可冒充推送**：任意登录用户可指定他人 user_id/alias 发极光通知，接口注释自定性为调试口，上线前需要加管理员鉴权或下线。
2. **极光通知不判在线**：RealtimePushUsecase 无条件双发（WS + JPush），在线用户也收到系统通知，去重依赖客户端。
3. **RefreshUser 死代码**：融云昵称/头像刷新无调用方，用户改资料后融云侧展示名可能滞后（GetToken 对已存在用户是否刷新资料取决于融云行为，本仓未做显式同步）。
4. **外部调用零指标**：JPush/融云客户端没有 Prometheus 打点（无调用次数/延迟/错误码指标），第三方故障只能靠日志与 5xx 间接发现。
5. **非原子写**：好友接受（关系+申请状态）、消息备份（整批）、群创建（融云+本地）都不是事务/补偿模型，失败存在中间态（§5.2/§5.3/§5.4 已标注）。
6. **N+1 查询**：好友列表、申请收件箱逐条 FindByUserID；好友量大时有性能隐患（已有 ListProfiles 批量方法可复用）。
7. **手机号搜索**：FindByPhone 用行内 regexp_replace 无法走索引；好友申请只拦同向 pending，可产生双向 pending。
8. **单聊准入是建议性的**：消息走客户端 ↔ 融云直连，BFF 无法强制好友关系；admission 接口仅给客户端自查。
9. **解散群不删成员行**；门店群移除成员不删本地映射；GetStoreGroup 查无复用 free-group 哨兵。
10. 平台枚举不一致：push CHECK 含 ohos 而 normalizePlatform 归并为 harmony。

## 7. 学习要点回顾

1. **指标低基数是红线**：route label 用 FullPath 模板、未匹配统一 `unmatched`、状态码归并成五段；自建 Registry 精确控制暴露内容。
2. **告警表达式防呆**：比率分母 `clamp_min` 防除零；P99 用 histogram_quantile on bucket；抓不到目标用 `up==0`。
3. **外部客户端的统一套路**：凭证占位识别（PLACEHOLDER）、未配置可构造、调用时 ErrNotConfigured、超时 10s、响应体限 1MB、错误带响应体、usecase 面向接口持有。
4. **usecase 的降级语义**：JPush 的不可用被设计成 `Skipped` 结果而非错误（推送是旁路能力）；而 IM 建群/拉人失败直接失败（核心链路）。旁路与主路的失败策略要有意区别。
5. **幂等设计**：设备 upsert（唯一索引+ON CONFLICT）、消息备份（message_uid 唯一+InsertIgnore）、好友关系（字典序单行+DoNothing）、门店群（确定性 ID+upsert）。
6. **跨域端口上提**：ImStoreGroupSyncer 放 shared 包，让 access/profile 域依赖抽象而不是 im 实现，避免域间直接 import（与 [04](04-HTTP路由与中间件.md) authctx 叶子包同款手法）。
7. **安全覆盖客户端输入**：备份接口的 user_id 用 json:"-" 拒绝客户端值、强制写会话身份；但 /push/send 的 targetUser 没有同等约束——区别对待的两面对照。
8. **双保险 schema 管理**：原生 SQL（CHECK、部分索引、复合主键这些 GORM 标签表达不了的东西）+ AutoMigrate 并存，embed SQL 进二进制保证随发布生效。
