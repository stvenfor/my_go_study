# 一、mall 域：门店商城与本地模拟支付

源码锚点：[app/internal/mall/](file:///Users/qpy/Desktop/github/my_go_study/app/internal/mall)、SQL [mall_schema.sql](file:///Users/qpy/Desktop/github/my_go_study/app/internal/repository/postgres/sql/mall_schema.sql)、实体 [mall.go](file:///Users/qpy/Desktop/github/my_go_study/model/entity/mall.go)。

通俗理解：标准电商骨架——类目、SPU 商品、SKU 规格（价格/库存/虚拟发货方式）、兑换码池、购物车、订单+订单行快照+状态日志、支付单、退款单、审计日志。刻意简化处：无物理外键、不接真实支付渠道（渠道 1-4 任意选都直接成功）、下单不锁库存（支付时才扣减）、已支付取消不回滚库存和码。

`PayOrderLocal` 事务内部顺序（[repo_postgres.go 第 284-483 行](file:///Users/qpy/Desktop/github/my_go_study/app/internal/mall/repo_postgres.go#L284-L483)）：

1. `SELECT ... FOR UPDATE` 锁订单+归属校验；已支付/已履约直接幂等返回当前详情；非 unpaid 返回 ErrOrderNotPayable。
2. 逐行履约：实体 SKU 执行 `UPDATE ... SET stock=stock-qty WHERE stock_qty>=qty`，0 行即库存不足回滚；虚拟-内容地址把 content_url 回写订单行；虚拟-兑换码 `FOR UPDATE SKIP LOCKED` 取 qty 个未用码（不足 ErrCodeInsufficient），逐条条件置 issued 并绑 order_item_id。
3. 写支付单：有积分→先写一张 channel=5、金额 0.00、payload 带积分数的成功单；CNY 金额非 0→再写一张传入渠道的成功单（纯积分订单支付渠道落 5）。
4. 条件 UPDATE 订单 unpaid→paid（payment_channel、paid_at），0 行→ErrOrderNotPayable；写状态日志；写 audit_log(payment.success)；重读装配详情返回。

`CreateOrder` 流程：idempotency_key 必填→先查重（命中直接返回旧单详情）→逐行取 SKU/商品：在售、**必须同一门店**（ErrMultiStore）、**整单支付方式必须一致**（ErrPaymentModeMixed，CNY/积分/混合不能混单）、实体品检查库存并标记需要收货地址→金额用 big.Rat 累加避免浮点误差、积分累加→实体品必须三件收货信息齐全→生成订单号 `O+去横线 UUID 前 20 位`、建单+行+日志一个事务→唯一约束冲突时再查重兜底幂等→可选清购物车。注意**下单不扣库存**，超卖由支付时的条件 UPDATE 拦截。

`PayOrder` 流程：渠道白名单（1-6）→取单验归属→超时先惰性取消返回 ErrOrderPayExpired→需要 CNY 时渠道必须是人民币渠道（1/2/3/4/6，否则 ErrNeedCNYChannel）；纯积分单渠道强制改为 5→先扣积分（pointsSvc.Debit，reason=mall_pay）→渠道 6 再扣钱包余额（ParseYuanToFen，walletSvc.Debit，reason=mall_pay）→`PayOrderLocal` 事务落库；落库任一步失败 `restorePayDebits` 退回。渠道 1-4（支付宝/微信/IAP）**不做任何渠道调用，直接当成功**。

## 1.6 请求链路（混合支付）

`POST /orders/:id/pay {payment_channel:6}` → 渠道校验/归属/TTL → 判定 needsPoints 与 needsCNY → pointsSvc.Debit 扣积分（独立事务、写积分流水）→ walletSvc.Debit 扣余额（行锁钱包+现金流水）→ PayOrderLocal 大事务：锁单→扣实体库存/发码→写积分支付单+CNY 支付单两张→订单置已付→日志→审计→返回详情。任一步失败：积分与余额分别 Credit 补偿（无 saga 编排，靠反向调用）。

## 1.7 假实现边界与种子

- 「本地模拟支付」：渠道 1-4 不调 payment 域、不调任何外部接口，任意渠道直接成功；payment 域的 Prepay 在商城链路中**没有被调用**。
- 取消已支付订单：退钱走钱包/积分内部账，不写 wys_mall_refund、不回补库存、兑换码不回收（ADR-0015 注释）。
- 没有履约发货接口（status=2 已履约无任何代码推进）；没有类目管理接口（category 表空转）；虚拟码买家侧没有查询已发码的专门接口（只在订单行 order_item_id 上有绑定）。
- 种子 [repo_seed.go](file:///Users/qpy/Desktop/github/my_go_study/app/internal/mall/repo_seed.go)（包级 EnsureSeed，main.go local 分支调用）：门店 1 在售商品不足 35 条时按 17 个规格模板循环补齐到 35（实体/虚拟交错、封面用 picsum、虚拟品发内容地址 example.com）；再幂等补 2 个积分演示 SKU：SEED-PTS-ONLY 纯积分 100 分兑换券、SEED-PTS-MIX 9.90 元+50 分混合礼包。

## 3.5 请求链路（延迟自动过审）

- Profile 的 role_badge/store_name 是预留空字段。

`CreateRecord` 事务：若带 appointment_id → `FOR UPDATE` 锁预约→必须属于同店且 pending（否则 ErrBadAppointment）→条件 UPDATE 置 done（0 行 ErrBadAppointment）→插记录；记录插入撞预约部分唯一索引时经 `shared.IsUniqueViolation` 归一为 ErrAppointmentTaken。

## 4.5 请求链路（从预约创建记录）

`POST /records {appointment_id:7, service_kind:"maintenance", title:"二保"}` → 当前店+成员校验 → FOR UPDATE 锁预约 7（同店、pending）→ 姓名从预约快照补 → 插记录 + 预约置 done 同一事务提交（部分唯一索引防两个请求同时转化同一预约，第二个得 ErrAppointmentTaken→409）。

## 4.6 假实现边界与种子

- 没有更新/删除记录接口；没有审核流；没有技师、工时、配件、费用字段。
- 客户视角只按 customer_user_id 字符串匹配，手机号同名不做归并；customer_user_id 由创建人手工传入，无校验该用户真实存在。
- 本域**没有 EnsureSeed**（main.go 只调 EnsureSchema）；列表里的预约数据依赖 home 域种子。
- 没有 C 端客户自己创建记录的路径（客户只读）。

# 学习要点回顾

1. 电商下单的三个经典防护在本仓的落点：幂等键唯一索引（CreateOrder 先查后插+冲突回查）、支付窗口惰性取消（读时状态迁移，同 short_video 的惰性过审是同一思想）、库存扣减放支付事务并以条件 UPDATE 兜底防超卖。
2. 金额处理两派：mall 内部用 big.Rat 累加再 FloatString(2)（decimal 思维、numeric 列存字符串），wallet/points 用整数分/积分；跨域支付时 ParseYuanToFen 桥接。不要在业务代码里用 float64 算钱（对比 purchase_calculator 的简化做法）。
3. 混合支付的账务拆单：一笔订单两张支付成功单（积分 0 元单 + CNY 单），唯一索引相应改为 (order_id, channel)；补偿也是两条独立反向流水，没有分布式事务框架。
4. 「预留表」要识别：wys_mall_category 无代码路径、wys_mall_refund 无写入路径——表里有的能力不等于系统有的能力，读代码以调用链为准。
5. 冗余计数的一致性：community 的 like_count/comment_count/heat 在事务内随行为更新并提供 Backfill 校正；short_video 只有 like_count/view_count；这类计数器都接受最终校正而非强一致全量重算。
6. 读时驱动状态机：订单超时取消、视频延迟过审、预约列表口径，全部在查询路径里顺手推进状态，省掉定时任务，代价是状态迁移依赖「有人来读」。
7. 端口适配的过渡形态：community.PushNotifier 是批 3/批 4 切片之间的临时桥，main.go 里留适配器并写清删除条件——阅读这种代码要能区分「长期架构端口」与「迁移期脚手架」。
8. 双视角数据隔离：after_sales 用「成员看全店、客户看自己」两套查询方法 + 读取时 canReadRecord 兜底，是不依赖权限码的粗粒度隔离示例。
