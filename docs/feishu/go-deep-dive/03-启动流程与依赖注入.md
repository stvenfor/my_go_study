# 03 · 启动流程与依赖注入（api 680 行装配全表 / worker / 四个工具命令）

> 一句话定位：本篇把六个 `main.go` 的启动顺序和「谁 new 了谁、按什么开关 new」逐行列清；所属模块为 app/cmd（可执行层），被装配的代码横跨 app/common/core/model；阅读前置：读 [01-工程结构与go-work多模块](01-工程结构与go-work多模块.md) 了解模块边界，读 [02-配置体系](02-配置体系.md) 了解开关字段。

## 通俗理解：main.go 是「手工装配车间」

这个项目**没有用 wire、fx 这类依赖注入框架**。`run()` 就是一个超长装配函数：自己读配置、自己连数据库、自己按开关 `New` 出一个个 Service，再把它们手工塞进 Router。

好处是整条链路一眼能从头看到尾；代价是 main.go 长（api 680 行），而且大量变量先声明成 `nil` 指针、再在 local / supabase 两个分支里择一赋值。记住一个阅读技巧：**先找三个布尔/分叉——`cfg.Auth.IsLocalProvider()`、`cfg.Supabase.Enabled()`、`businessEnabled`——剩下的代码都是「开关为真时多装一块」。**

## 学习要点回顾

1. 这是纯手工 DI：所有依赖在 run() 里显式 New 并按构造顺序传参；新增依赖要改三处——构造、router.Options、路由注册。
2. 三开关读全文：IsLocalProvider、Supabase.Enabled、businessEnabled；大量 nil 指针 + `if svc != nil` 就是开关的物化形式。
3. local 与 supabase 是「同一接口、两套仓储」的分叉：ProfileRepository、transaction repo、sessionAuth 中间件、gRPC authenticator 都有双实现。
4. 可选依赖用「后置 Setter」：SetSearchStore、SetOfflinePusher、SetStoreGroupSync，解决可选能力与循环关注。
5. 启动期所有建表/种子失败几乎都只 Warn 不退出（autoMigrate、EnsureSchema、EnsureSeed），保证依赖没就绪时 API 仍能起来；唯独连库、Supabase 客户端、RabbitMQ（queue 开启时）失败会退出。
6. worker 与 api 通过 RabbitMQ（任务）+ Redis Pub/Sub（在线扇出）解耦：api 有 Subscriber、worker 有 Publisher，两端共用频道名 `realtime:fanout`。
7. 四个工具命令共享 config.Load+NewPostgres 起步模式，但刻意不初始化 Zap；import-supabase 自带一份最小 schema 准备逻辑，可独立于 api 运行。
8. 优雅关闭有严格顺序：先停流量入口（gRPC/HTTP）再关队列，数据库连接交给 defer 最后关。
