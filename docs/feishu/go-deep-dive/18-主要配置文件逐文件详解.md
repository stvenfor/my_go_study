# 18 · 主要配置文件逐文件详解（磁盘上的每一个键）

> 一句话定位：[02-配置体系](02-配置体系.md) 讲的是「Config 结构体字段与 Viper 加载机制」（内存侧），本篇把视角翻到磁盘侧——把仓库里每一个 YAML / env / compose / Makefile / Dockerfile 配置文件逐行、逐键拆开，讲清「这个文件被谁读、键值是什么、与 base 差在哪、最终流进哪个进程」。阅读前置：[01-工程结构与go-work多模块](01-工程结构与go-work多模块.md)、[02-配置体系](02-配置体系.md)。

## 通俗理解：配置文件是「印好的菜单、便签、口头叮嘱和打包行李」

- `configs/config.yaml` 是**印好的标准菜单**：109 行，所有键的默认值都在这。
- `config.dev/lan/prod.yaml` 是**贴在菜单上的便签**：只写和标准不一样（或刻意重复强调）的几行。
- `.env*` 是**服务员的口头叮嘱**：先被 shell `source` 成环境变量，Viper 再按名字取走。
- `docker-compose.yml` 是**给后厨（容器）的正式工单**：把宿主机叮嘱翻译成容器里的环境变量。
- `Dockerfile` 是**打包行李清单**：镜像构建那一刻，四份 YAML 就被 COPY 进镜像了——这正是「改了配置不生效」的头号原因。

本篇所有事实均实读原文，锚点格式为 `相对路径:行号`。

## 2. 四份 YAML 逐文件详解

Viper 侧机制先钉死（详见 [02-配置体系](02-配置体系.md) 的 12 阶段表）：`config.yaml` 用 `ReadInConfig()` 整体读入（config.go:631-633），`config.<env>.yaml` 用 `MergeInConfig()` 合并（config.go:635-640）。合并是 map 深合并：嵌套段里没写的键保留 base 值，标量键**即使写空串也会覆盖**（lan 文件的 `dev_test_phone: ""` 即此用法）；环境文件不存在直接报错，不静默回落。

## 4. 覆盖优先级实证

### 4.1 APP_ENV 怎么选文件（带行号）

1. **取值与兜底**：六个 cmd 入口同款写法——api 在 app/cmd/api/main.go:76-79（`os.Getenv("APP_ENV")`，空串兜底 `"dev"`），worker 在 app/cmd/worker/main.go:34-37，import-supabase:53、scheduler-trigger:16、seed-analytics:20、seed-home-todo:17 同模式。
2. **传进 Load**：main.go:81 `config.Load(config.ResolveConfigDir(), env)`。
3. **定位目录**：ResolveConfigDir（config.go:843-860）从 cwd 逐级向上找 `configs/` 目录，找不到返回相对名 `"configs"`。容器内 WORKDIR=/app（Dockerfile:47），configs 就在 /app/configs。
4. **改名 + 合并**：config.go:635-640——env 非空时 `v.SetConfigName("config." + env)`（:636）后 `MergeInConfig()`（:637）；文件缺失返回「读取环境配置 config.%s.yaml 失败」错误（:638），**不会静默回落到 config.yaml**。env 为空则跳过整段（main 又总会兜底 dev，所以裸跑 Go 也是 dev）。
5. **写回结构体**：config.go:794 `cfg.AppEnv = strings.TrimSpace(env)`——AppEnv 只来自 APP_ENV，与 yaml/gin mode 完全无关。

### 4.2 yaml 与 env 谁赢：Viper 调用顺序实证

Load 内的真实顺序（config.go:625-722）：

| 顺序 | 代码 | 对优先级的意义 |
|---|---|---|
| 1 | ReadInConfig :631 | config.yaml 入 Viper 的 config 层 |
| 2 | MergeInConfig :637 | config.<env>.yaml 深合并覆盖 config 层 |
| 3 | SetEnvKeyReplacer(".","_") + AutomaticEnv :642-643 | 任意 `a.b` 键可隐式查 `A_B` |
| 4 | 70+ 个 BindEnv :646-717 | 显式「键↔变量名」契约，含多候选名（anon_key 同时认 SUPABASE_ANON_KEY/SUPABASE_KEY :658） |
| 5 | Unmarshal :720 | 此时 Viper find 顺序为 显式 override > pflag > **环境变量 > config 文件** > 默认 |

实证结论：

- **环境变量赢 yaml**。同名键只要 env 被设置（BindEnv 显式绑定的那些），容器/export 的值压过两份 YAML。例：docker-compose.yml:86 固定 `DATABASE_HOST: postgres`，所以容器内无论 dev/lan yaml 写什么 host，都连服务名 postgres。
- **项目没有用 `v.SetDefault()`**（全 common/config 目录 grep 零命中）。Viper 层不存在「默认层」；02 篇列的出厂默认全部由 Go 代码在 Unmarshal **之后**回填（config.go:735-792、applySSEDefaults :802-840），所以它们是整条链里优先级最低的网底。
- **空串 env 也算数的坑**：compose 里 `AUTH_PROVIDER: ${AUTH_PROVIDER:-}`（docker-compose.yml:84）会向容器导出一个**空但已设置**的环境变量，Viper 显式 BindEnv 查找时它压过 yaml。dev 文件本就没写 provider（空→supabase 兼容），结果一致；但理解这点能解释「为什么 compose 里写 `:-` 和不写这行不等价」。lan overlay 相应地写成 `:-local`（docker-compose.lan.yml:15）保底。
- **只补空值的文件读取**：applySupabaseDefaults（:875-880）与 applyLocalEnvDefaults（:898-900）都先判空再填，永远不覆盖 yaml/env 已给的值。
- 唯一硬校验：jwt.secret 空→报错（:732-734）。

### 4.3 make run 实际 export 了哪些文件

调用链：`make run`（Makefile:24-25）→ `./scripts/load-env.sh go -C app run ./cmd/api` → load-env.sh:7 `source scripts/source-env.sh` → load-env.sh:8 `exec "$@"`。

source-env.sh 全文只有三条 source，且包在 `set -a`（:4）里——source 进来的赋值**全部自动 export**：

1. configs/supabase.env（:5-8，存在才 source）
2. 项目根 .env（:9-12，存在才 source）
3. 项目根 .env.local（:13-16，存在才 source）

后者覆盖前者同名键（shell source 的天然语义）。`make run-worker`（Makefile:27-28）、import-supabase（:135）、seed-analytics（:142）、trigger-hourly-notify（:177）全部走同一条 load-env.sh。

要点：

- **make run 不加载 .env.lan**。只有 lan-compose.sh:24-27（compose 路线）和 lan-run.sh:20-23（本机进程路线）显式 source .env.lan，且都在 source-env.sh **之后** source——.env.lan 同名键赢。
- 不经过 load-env.sh 直接 `go -C app run ./cmd/api` 时，.env 不会变成环境变量（Go 的 applyLocalEnvDefaults 只会从文件里捞 service_role 一个字段，:885-903），这是「env 没生效」最常见原因。

### 4.4 compose environment 与容器内 env 的关系

- 两份 compose **都没有 `env_file:` 段**（docker/ 目录 grep 零命中）。容器变量只有一个来源：`environment:` 里的 `${VAR}` 占位，在 compose 启动那一刻由**包装脚本 source 出来的 shell 环境**做字符串替换。
- 基础路线 `make docker-up`：docker-compose.sh:10 source source-env.sh（supabase.env→.env→.env.local），:12 `docker compose -f docker/docker-compose.yml`。
- LAN 路线 `make lan-up`：lan-compose.sh:11 先 source-env.sh，:13-16 强制 .env.lan 必须存在，:19-22 up/build 前先 sync-lan-ip，:24-27 再 source .env.lan（赢），:29-32 校验 REALTIME_PUBLIC_WS_HOST 非占位，:34 兜底 APP_ENV=lan，:36-38 用 `-f 基础 -f lan overlay` 两份文件启动；overlay 的 environment 与基础合并覆盖。
- app 服务环境变量白名单：docker-compose.yml:82-108（26 个键，含 APP_ENV、AUTH_PROVIDER、DB/Redis/RabbitMQ/ES、JWT、QUEUE_ENABLED、GRPC_*、SUPABASE_*、AUTH_*、RONGCLOUD_*）；worker 精简版 :136-150；overlay 增量（lan.yml:13-40）强制 APP_ENV=lan、AUTH_PROVIDER 默认 local、QUEUE_ENABLED="true"、REALTIME_PUBLIC_WS_HOST 必填（:28 用 `${VAR:?报错信息}` 语法，缺失直接拒绝启动）。
- 容器里这些 env 再被 Viper BindEnv/AutomaticEnv 取走（同 4.2）。compose 给的默认值（如 JWT_SECRET :94 `change-me-in-production`、ES :93 `http://elasticsearch:9200`）只在宿主机没 export 时生效。

## 7. 常见问题：改了配置为什么不生效

1. **Docker 把配置在构建时冻进镜像了。** Dockerfile:57-59 在 build 阶段 `COPY --from=builder /app/configs /app/configs`，四份 yaml 与（构建机上存在的）supabase.env 都在镜像里。改 yaml 后只 `up -d` 不 `--build`，容器跑的还是旧文件；lan-compose.sh:5 注释也明确「改 Go 代码后须带 --build 重建；仅改 env 也建议 down 后再 up」。反过来 .env 类文件**不在**最终镜像里（最终阶段只 COPY bin 与 configs；.dockerignore:9-10 还排除了 .env.local/.env.lan），它们靠 compose environment 每次启动重新注入——所以 yaml 改动要 rebuild，env 改动要重新 up。
2. **env 没有被 export 进进程。** 直接 `go -C app run ./cmd/api` 不会 source 任何 .env；Go 进程直接读文件只捞 service_role（config.go:885-903），DATABASE_HOST 等一律拿不到，回落 yaml 的 localhost。要走 `make run`（load-env.sh:7）。另外 `.env.lan` 只有 lan-up/lan-run 两条路加载，普通 make run 不读它。
3. **APP_ENV 选错了文件。** 不 export 时六个 main 一律兜底 dev（main.go:77-79 等）；APP_ENV 写了不存在的值（如 typo `deev`）会在 MergeInConfig 直接报错退出（config.go:637-639）而不是静默回落；make lan-up 时 overlay 强制 APP_ENV=lan（docker-compose.lan.yml:14、:44），shell 里 export 别的值也会被 compose 文件里的字面值盖掉。
4. **YAML 缩进 / merge 认知错误。** MergeInConfig 是按 map 深合并：键缩进错一层就变成另一个段（Viper 不报错，Unmarshal 后静默零值）；标量写空串 `""` 也是有效覆盖（lan 的 dev_test_* 即此）；环境文件是「便签」不是「替换」——删掉便签里的键只会回退 base，不要指望在便签里删键能「关掉」base 配置（要显式写 false/空串）。
5. **env 名字没在映射契约里 / 空串覆盖。** 只有 config.go:646-717 显式 BindEnv 的约 70 个名字是契约；`DATABASE_SSLMODE`、`LOG_LEVEL`、`REDIS_DB` 没绑定，AutomaticEnv 的隐式命中不算项目承诺（02 篇已标 ⚠️）。切片变量（白名单类）用逗号分隔。再就是 compose `${AUTH_PROVIDER:-}` 会导出空串，空但已设置的 env 在 Viper 里同样压过 yaml——排查时以容器内 `printenv` 实际值为准，不要只看 yaml。

## 学习要点回顾

1. 磁盘配置分四类：base YAML（必读）、env YAML（merge）、env 文件（shell source + Go 只补空值双通道）、compose environment（每次启动现注入）；模板 .example 不给程序读。
2. 四份 YAML 的全部差异可压缩成 10 个键：mode、log.level、sslmode、auth.provider、dev_test_* 三键、queue.enabled、push_async、scheduler 两个开关。
3. APP_ENV 三处作用：选 config.<env>.yaml（config.go:636）、写 cfg.AppEnv（:794）、参与非正式环境判定；选不到文件直接报错。
4. 优先级实证：env > merge yaml > base yaml；项目无 SetDefault，Go 代码回填（:735-792）是最低网底；jwt.secret 是唯一硬必填。
5. shell 侧加载顺序 supabase.env → .env → .env.local（source-env.sh:5-16，后者覆盖前者）；.env.lan 只在 LAN 两条路加载且最后 source。
6. compose 不用 env_file，全靠包装脚本 source 后做 `${VAR}` 替换；overlay 用 `:?` 把 REALTIME_PUBLIC_WS_HOST 变成启动期硬校验。
7. 镜像在 build 时冻结 configs/（Dockerfile:59），改 yaml 要 --build；.env 不进镜像，改 env 要重 up——这是「不生效」问题的分界岭。
8. 入库纪律：.env 与 configs/supabase.env 刻意入库（dev 默认值 + 公开 anon 常量），.env.local/.env.lan 刻意不入库；service_role 有 AGENTS 三处规则 + check-secrets.sh + 双 ignore 四道防线。
9. 客户端（my_ai_project）靠 --dart-define-from-file 读 .env/.env.lan：Android 模拟器 10.0.2.2、iOS 模拟器直通、真机必须注入 BACKEND_HOST；IP 由 Go 仓 sync-lan-ip 双向自动写。
10. change-me-in-production 在 compose 里是生产默认值，意味着「忘配 JWT_SECRET 也能起生产」——默认值帮你跑起来，不代表默认值安全。
