# 06 · 通用业务域：权限门店、首页待办、支付、钱包、积分与会员

> 一句话定位：六个「与汽车业务无关、所有 App 都可能有」的垂直切片——access（门店与 RBAC）、home（首页待办聚合）、payment（微信/支付宝预下单通道）、wallet（人民币钱包）、points（积分签到成长任务）、membership（会员订阅与 IAP）。所属模块：app 模块 `app/internal/<域>/`。阅读前置：懂 GORM 基本用法、Gin 路由组与中间件、第 04 篇的 SessionAuth 双认证背景。

## 本篇怎么读

通俗理解：这六个域是 App 的「水电煤」。access 是公司的门禁卡和组织架构图；home 是店长手机首页的「今天要处理的几件事」汇总屏；payment 是收银台的 POS 机（只负责唤起微信/支付宝，不记账）；wallet 是你在 App 里的电子零钱罐；points 是打卡发积分的小账本；membership 是视频网站式的「开通 SVIP」。

六个域全部遵循五件套结构，唯一例外是 payment 没有 repository（它不落库，纯外部通道封装）。

| 域 | 包路径 | 五件套 | 自有表 |
| --- | --- | --- | --- |
| access | `app/internal/access/` | router/handler/service/repository/repo_postgres | wys_store、wys_store_member、role、permission、role_permission、user_role、wys_user_store_stats |
| home | `app/internal/home/` | 五件套 + repo_seed | wys_store_join_application、wys_store_customer、wys_after_sales_appointment、wys_store_review_order、wys_home_todo_packing_demo |
| payment | `app/internal/payment/` | router/handler/service（无 repo） | 无 |
| wallet | `app/internal/wallet/` | 五件套 | wys_cash_wallet、wys_cash_ledger、wys_bank_card |
| points | `app/internal/points/` | 五件套 + repo_task_progress | wys_points_wallet、wys_points_ledger、wys_check_ins、wys_task_claims |
| membership | `app/internal/membership/` | 五件套 + iap_apple + iap_huawei | wys_membership_entitlement、wys_membership_order |

共享中间件链：所有路由组都用 [http.go](file:///Users/qpy/Desktop/github/my_go_study/app/internal/shared/http.go#L10-L16) 的 `shared.SessionAuthChain(sessionAuth, accountGate)` 拼装，等于「Session Auth 必选 + 账号激活状态门可选」。Router 里还有一个共同约定：`sessionAuth == nil` 时 `Register` 直接整体跳过，等于配置关了业务认证就不挂这些路由。

# 一、access 域：门店、成员与角色

源码锚点：[app/internal/access/](file:///Users/qpy/Desktop/github/my_go_study/app/internal/access)、SQL [access_control.sql](file:///Users/qpy/Desktop/github/my_go_study/app/internal/repository/postgres/sql/access_control.sql)。

通俗理解：这个域回答三个问题——「有哪些店」「谁在哪家店、当什么职务」「谁能干什么事」。注意它刻意区分了两个概念：**职务**（position：销售顾问/经理/总经理，只是个头衔）和**权限**（role 带来的 permission code，才是能不能调某个接口的真正依据）。

## 1.1 表结构

| 表 | 关键字段 | 说明 / 约束 |
| --- | --- | --- |
| `wys_store` | store_id（integer 主键，>0）、name | 门店。多名用户可同属一家 |
| `role` | code（主键）、scope（platform/store）、name | 内置三种角色，运行时不新建 |
| `permission` | code（主键）、name | 能力码，只有授予没有拒绝（无 deny 语义） |
| `role_permission` | role_code + permission_code 联合主键 | 角色→能力多对多，外键均 ON DELETE RESTRICT |
| `wys_store_member` | user_id + store_id 联合主键、position smallint | 一人一店一职务；position CHECK 限定 0/1/2（0 销售顾问、1 销售经理、2 总经理） |
| `user_role` | user_id、role_code、store_id（可空）、granted_by | 角色分配；平台行 store_id 为空、店内行必须有店；两个部分唯一索引分别约束这两种情况 |
| `wys_user_store_stats` | user_id + store_id 联合主键、days_joined、employee_count 等 | 某人在某店的展示数字（遗留统计卡，不是成员名单）；role 列注明「遗留职务列，资料接口不读」 |
| `users.current_store_id` | — | SQL 末尾补外键到 wys_store；悬空值置 NULL；语义是「当前选中店，切换时还须已是该店成员」 |

SQL 启动时还幂等灌入种子：3 个角色（platform_admin / store_admin / store_staff）、8 个权限码（store.create、member.write、role.assign_store、role.assign_platform、profile.read、transaction.read_own/write_own/read_store）、16 行 role_permission 绑定。platform_admin 拿全部 8 个；store_admin 没有 store.create 和 role.assign_platform，其余 6 个；store_staff 只有 profile.read + transaction.read_own/write_own。

| 方法/函数 | 职责 | 关键逻辑 / 坑 |
| --- | --- | --- |
| `NewService(repo) *Service` | 构造 | — |
| `SetStoreGroupSync(syncer shared.ImStoreGroupSyncer)` | 注入 IM 门店群同步 | 带 nil 接收者保护 |
| `CreateStore(ctx, actorID, storeID, name) (*WysStore, error)` | 建店 | 校验 storeID>0、name 非空；要求 store.create；**不自动让操作者成为成员** |
| `UpsertMember(ctx, actorID, storeID, targetUserID, position int16) (*WysStoreMember, error)` | 加人/改职务 | position 限定 0-2；要求 member.write；先验店存在、目标用户存在；成功后尽力调 IM `EnsureStoreMembership`（错误只吞不阻断） |

| `ListEffectivePermissions(ctx, userID, storeID int) ([]string, error)` | 平台 ∪ 店内能力码去重 | storeID<=0 时回退读 users.current_store_id；非成员则只给平台权限 |
| `RequirePermission(ctx, actorID, permission string, targetStoreID *int) error` | 对外暴露的硬校验 | 商城写目录等跨域场景调用；失败即 ErrForbidden |
| `Can(ctx, actorID, permission, targetStoreID *int) (bool, error)` | 同上但返回 bool | 调用方想「降级只读」时用；new_car_follow 在用 |
| `CurrentStoreID(ctx, userID) (*int, error)` | 当前店（nil 安全） | access 未接线（Service 为 nil）时返回 nil,nil |
| `RequireCurrentStore(ctx, actorID, noStore error) (int, error)` | 取当前店或返回调用方给定错误 | 汽车业务各域常用 |
| `IsMember(ctx, userID, storeID) (bool, error)` | 成员判定 | ErrMemberNotFound 归一成 (false,nil)；nil 安全 |
| `StoreLabels(ctx, actorID, storeID) (storeName, positionLabel string)` | 摘要页门店名/岗位文案 | 读不到返回空串；岗位文案走 `entity.StoreRoleLabel` |
| 私有 `require / can` | 权限内核 | can 的判定顺序：平台码直接通过→权限不需要店则拒→targetStoreID 必填→操作者 current_store_id 必须等于目标店→必须是成员→店内码包含才通过 |

通俗理解 `can`：平台管理员是「全国通行证」；店内权限必须同时满足三张牌——手里有这张权限牌、当前切换到的就是这家店、本人确实是这家店成员，缺一不可。

## 1.6 请求链路（以授店内角色为例）

1. `POST /api/v1/roles/assignments` → SessionAuth 解析业务 token、写身份；accountGate 校验账号激活。
2. `handler.AssignRole` 绑定 body，调 `Service.AssignRole(actorID, targetUserID, roleCode, storeID)`。
3. Service `GetRole` 拿 scope；店内分支调 `require(role.assign_store)` → `can`：平台码没有 → 查 current_store_id → `GetMember` 验成员 → `StorePermissionCodes` 包含性检查。
4. 再 `GetMember(目标用户, 店)` 确认被授权人也是成员。
5. `repo.AssignRole` 执行幂等 INSERT，返回。

## 1.7 假实现边界与种子

- 角色/权限/绑定全部是 SQL 种子，代码不提供「新建角色」接口（role 表注释明示）。
- IM 门店群同步是可选端口：没接线时 `storeGroupSync == nil`，入店/离店只写库不拉群；接线后失败也只吞掉（`_, _ =`），不影响主流程。
- `wys_user_store_stats` 是旧统计卡迁移表，access 代码不写它，仅 SQL 做数据兼容（补门店、改主键、补外键）。

# 三、payment 域：微信 / 支付宝预下单

源码锚点：[app/internal/payment/](file:///Users/qpy/Desktop/github/my_go_study/app/internal/payment)。

# 学习要点回顾

1. 垂直切片五件套的标准协作：Router 只挂链与路由，handler 只做协议适配，权限与事务在 service，SQL 全在 repo；错误哨兵定义在「拥有该错误语义」的包（payment 在 service、其余在 repository）。
2. RBAC 的两张牌分离：position 是职务头衔，role→permission 才是能力；店内权限三连判定（当前店匹配 + 成员关系 + 角色持有）是跨域复用最频繁的规则。
3. 「余额 + 流水」模型在 wallet 和 points 出现两次：同一套 `SELECT FOR UPDATE` + upsert 钱包行 + 快照流水事务，是学习资金类并发的最小范本。
4. 幂等手段集锦：部分唯一索引（pending 入店申请）、条件 UPDATE 防双审、out_trade_no 唯一索引防 IAP 重复发卡、ON CONFLICT DO NOTHING。
5. 跨域协作靠端口而非具体类型：points 的 TaskProgressSource、access 的 ImStoreGroupSyncer、membership 的两个 IAP Verifier，均在消费方定义接口、由装配层注入，nil 即降级。
6. 假实现要显式：payment 未配置报 503、membership devMode 才允许跳过真验票、wallet 充值直接到账、华为通知是 stub——读代码先把这些边界划出来才不会误判系统能力。
7. 时区是业务正确性的一部分：待办「今天」、签到「当日」全部按 Asia/Shanghai 自然日，用字符串 yyyy-MM-dd 落库与比较。
8. home 域示范了「聚合层」写法：不持有业务，只按权限数别的域的表（甚至直接数 used_car 的表），配合装箱演示规格完成前端联调。
