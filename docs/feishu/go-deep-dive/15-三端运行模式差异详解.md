# 15 · 三端运行模式差异详解（make run / lan-up 容器 / 生产镜像）

> 一句话定位：同一份 Go 代码有三种「演出场地」——本机进程排练、局域网 Docker 带妆联排、生产容器正式公演；本篇把三种模式的启动链路、配置来源、端口实证、依赖供给、客户端接入逐项对齐。阅读前置：[01-工程结构与go-work多模块](01-工程结构与go-work多模块.md)、[02-配置体系](02-配置体系.md)、[03-启动流程与依赖注入](03-启动流程与依赖注入.md)。

## 通俗理解：三种模式是同一场话剧的三个场地

| 比喻 | 模式 | 入口 | 观众 |
|---|---|---|---|
| 排练厅，演员（Go 进程）直接站在你电脑上 | ① 本机进程 | `make run` | 只有你自己（127.0.0.1） |
| 带妆联排，全剧组（整套容器）在你 Mac 上搭台，手机进场看戏 | ② 局域网 Docker | `make lan-up` | 同一 Wi‑Fi 的真机 |
| 正式剧场，烤进镜像的剧目部署到机房 | ③ 生产容器 | Dockerfile + `APP_ENV=prod` | 公网/正式用户 |

舞台图纸（[docker/docker-compose.yml](file:///Users/qpy/Desktop/github/my_go_study/docker/docker-compose.yml)、[configs/](file:///Users/qpy/Desktop/github/my_go_study/configs)）和场务脚本（[scripts/](file:///Users/qpy/Desktop/github/my_go_study/scripts)）都是同一套，区别只在**谁来提供依赖、对外开哪扇门、拿哪份配置开演**。

## 0. 一页速览

| 维度 | ① 本机 dev | ② 局域网 lan（容器） | ③ 生产 prod |
|---|---|---|---|
| 命令 | `make run`（+`make run-worker`） | `make lan-up` / `make lan-down` | 镜像部署，`APP_ENV=prod` 跑 `/app/api` |
| APP_ENV | `dev`（空值兜底也是 dev） | 固定 `lan` | `prod` |
| 合并的 YAML | config.yaml + [config.dev.yaml](file:///Users/qpy/Desktop/github/my_go_study/configs/config.dev.yaml) | + [config.lan.yaml](file:///Users/qpy/Desktop/github/my_go_study/configs/config.lan.yaml) | + [config.prod.yaml](file:///Users/qpy/Desktop/github/my_go_study/configs/config.prod.yaml) |
| 进程形态 | 源码 `go run`，改完即生效 | 镜像内二进制，改 Go 必须 `--build` | 不可变镜像，发版替换 |
| Auth | 默认 Supabase Cloud（provider 为空即 supabase） | 强制 `AUTH_PROVIDER=local` | 默认仍为 supabase（见 §3.4 坑） |
| PG/Redis | Homebrew 或手动 Docker，走 localhost | compose 容器，走服务名 `postgres`/`redis` | 部署方提供，`sslmode=require` |
| 8080/9090 谁能连 | 进程监听全网卡，但设计上只给本机 | 映射 `0.0.0.0`，同 Wi‑Fi 可达 | 由部署平台决定 |
| WS 宣告主机 | `127.0.0.1` | `.env.lan` 的真实网卡 IP | 需注入正式域名（⚠️ 代码目前只拼 `ws://`） |
| 观测栈 | 默认无（除非手动起容器） | compose 全套 Prometheus/Grafana/… | 部署方自建 |

装配阶段本身三种模式完全相同（都是 [03 篇](03-启动流程与依赖注入.md)那 15 个阶段），差异全部来自**环境变量和 YAML 覆盖**。

### 1.3 端口绑定实证

- HTTP 服务地址写的是 `fmt.Sprintf(":%d", port)`（[api/main.go L531-L535](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L531-L535)），即监听全部网卡；gRPC 同样是 `net.Listen("tcp", ":9090")`（[grpc/server.go L53](file:///Users/qpy/Desktop/github/my_go_study/app/internal/delivery/grpc/server.go#L53)）。
- 但 dev 模式的依赖全部指向 `localhost`：`database.host: localhost`（[config.dev.yaml L10-L14](file:///Users/qpy/Desktop/github/my_go_study/configs/config.dev.yaml#L10-L14)），WS 对外宣告 `127.0.0.1`（config.yaml L55）。
- 结论：进程虽然理论上全网卡可达，但 dev 配置姿态是「只给本机用」；要让真机能连，请走模式②而不是裸 `make run`。

### 1.4 外部依赖谁提供

**路径 A：`make deps-up`（Homebrew）**，[Makefile L82-L93](file:///Users/qpy/Desktop/github/my_go_study/Makefile#L82-L93) 逐步做：

1. 缺 `postgresql@16` / `redis` 就 `brew install`；
2. `brew services start` 两者；
3. `sleep 2` 后检查 postgres 角色，没有就 `CREATE ROLE postgres WITH LOGIN SUPERUSER PASSWORD 'postgres'`；
4. `createdb my_go_study`（已存在则忽略）并授权。

它**只管 PG + Redis**。RabbitMQ、Elasticsearch 不由它提供：

- RabbitMQ：dev 把 `queue.enabled` 覆盖成了 true（[config.dev.yaml L28-L30](file:///Users/qpy/Desktop/github/my_go_study/configs/config.dev.yaml#L28-L30)），而 API 在队列开关为真时 `queue.NewClient` 连不上会**直接退出**（见 [03 篇](03-启动流程与依赖注入.md) 阶段 8）。所以只跑 `make deps-up && make run` 可能卡在连 RabbitMQ；常见补法是只起容器版依赖：`docker compose -f docker/docker-compose.yml up -d rabbitmq elasticsearch`。
- Elasticsearch：URL 为空就关闭搜索（config.yaml L68-L69），非必需；需要时设 `ELASTICSEARCH_URL=http://127.0.0.1:9200`（[config.dev.yaml L32-L34](file:///Users/qpy/Desktop/github/my_go_study/configs/config.dev.yaml#L32-L34)）。

**路径 B：`make docker-up`（dev profile 的容器近亲）**。它由 [scripts/docker-compose.sh](file:///Users/qpy/Desktop/github/my_go_study/scripts/docker-compose.sh) source 三个 env 后执行 `docker compose -f docker/docker-compose.yml up -d --build`，`APP_ENV` 默认 `${APP_ENV:-dev}`（[compose L83](file:///Users/qpy/Desktop/github/my_go_study/docker/docker-compose.yml#L83)）。也就是说：**它和 `make run` 是同一个 dev 配置画像，只是进程换成容器、依赖由 compose 供给**。无 Docker 时 target 直接报错并提示改用 `make deps-up && make run`（[Makefile L74-L80](file:///Users/qpy/Desktop/github/my_go_study/Makefile#L74-L80)）。

### 1.5 Auth provider

dev 的 YAML 和 [.env.example](file:///Users/qpy/Desktop/github/my_go_study/.env.example) 都不设 `AUTH_PROVIDER`。归一化逻辑里 provider 为空走 default 分支，返回 `supabase`（[config.go L175-L183](file:///Users/qpy/Desktop/github/my_go_study/common/config/config.go#L175-L183)）。因此模式①默认对接 Supabase Cloud，凭证来自 configs/supabase.env + `.env.local`；本地 Postgres Auth 是模式②才打开的分叉（两者装配差异见 [03 篇](03-启动流程与依赖注入.md) 阶段 6A/6B）。

## 2. 模式②：局域网 Docker `make lan-up`

通俗理解：把整个剧组（PG/Redis/RabbitMQ/ES/API/Worker/观测台）装进容器搭在你 Mac 上，对外只开两扇门——8080（HTTP/WS）和 9090（gRPC），手机凭同一 Wi‑Fi 和一个「门牌号 IP」进场。

### 2.1 启动命令逐步分解（函数级）

`make lan-up` 先检查 docker，再执行（[Makefile L110-L117](file:///Users/qpy/Desktop/github/my_go_study/Makefile#L110-L117)）：

```text
LAN_CLIENTS="..." ./scripts/lan-compose.sh up -d --build
```

[scripts/lan-compose.sh](file:///Users/qpy/Desktop/github/my_go_study/scripts/lan-compose.sh) 的函数级动作：

| 行 | 动作 | 失败行为 |
|---|---|---|
| L11 | source source-env.sh（supabase.env → .env → .env.local） | — |
| L13-L16 | 校验 `.env.lan` 存在 | 缺失报「请先 cp .env.lan.example .env.lan」exit 1 |
| L19-L22 | 子命令不是 down/stop/logs/ps/exec/top 时，先跑 `sync-lan-ip.sh`（带 `SYNC_LAN_IP_SKIP_DOCKER=1`） | 探测不到网卡 IP 则失败 |
| L24-L27 | 再 source `.env.lan`（**在最后，优先级最高**） | — |

| L34 | `export APP_ENV="${APP_ENV:-lan}"` | — |
| L36-L39 | `docker compose -f docker-compose.yml -f docker-compose.lan.yml "$@"` | overlay 叠加在基础文件上 |

### 2.2 IP 同步脚本做了什么（函数级）

[scripts/sync-lan-ip.sh](file:///Users/qpy/Desktop/github/my_go_study/scripts/sync-lan-ip.sh) 是 lan 模式的「门牌号刷新器」，三段逻辑：

**① 探测 IP（L18-L37，`detect_lan_ip`）**

1. `route -n get default` 取默认路由网卡名，再 `ipconfig getifaddr <iface>`；
2. 取不到就依次试 en0/en1/en2；
3. 空或 `169.254.*`（APIPA）直接报错「请确认 Mac 已连接 Wi‑Fi」。

**② 写 Go 侧 `.env.lan`（L55-L67）**：文件不存在则从 `.env.lan.example` 复制；`upsert_kv`（L39-L50）按 `^KEY=` 正则存在即 sed 替换、不存在则追加，刷新 `REALTIME_PUBLIC_WS_HOST=<IP>`。

**③ 内嵌 Python 刷各客户端（L72-L140）**：清单文件是 [scripts/lan-ip.clients](file:///Users/qpy/Desktop/github/my_go_study/scripts/lan-ip.clients)，规则详见 §5。

**④ 热修正在跑的容器（L142-L175，`refresh_running_app`）**：若容器 `my_go_study_app` 正在运行且 `printenv REALTIME_PUBLIC_WS_HOST` 已过期，用 `up -d --no-deps --no-build app` **只重建 app 容器、不重编译镜像**；`lan-compose.sh` 调用时用 `SYNC_LAN_IP_SKIP_DOCKER=1` 跳过这步（因为 compose 自己紧接着会 up）。

### 2.6 端口实证：127.0.0.1 与 0.0.0.0 的分野

- 基础 compose 给 pg/redis/rmq/es/prometheus/alertmanager/grafana 的端口字符串**全部带 `127.0.0.1:` 前缀**，家庭局域网扫不到；注释明说是「避免家庭局域网扫到 Postgres」（[compose L9-L11](file:///Users/qpy/Desktop/github/my_go_study/docker/docker-compose.yml#L9-L11)）。
- app 的 `"8080:8080"` 没有主机 IP，Docker 默认发布到 `0.0.0.0`——这是 lan 模式唯一对真机开放的业务入口（[lan-ops 文档](file:///Users/qpy/Desktop/github/my_go_study/docs/docker/lan-ops-abc-beginner.md) A4 节要求 `docker ps` 看到 `0.0.0.0:8080->8080`）。

### 2.7 Auth、代码生效、worker

- **Auth**：默认本地 Postgres Auth（`AUTH_PROVIDER=local`）；想切回 Cloud，在 `.env.lan` 设 `AUTH_PROVIDER=supabase`（overlay 注释 L8-L9），SUPABASE_* 由 source-env 提供。

- **worker**：compose 自动起同一个镜像的 worker 容器，无需另开终端；日志 `docker logs my_go_study_worker`。

### 3.4 prod 的两个必知坑（代码实证）

1. **Auth provider 空值会被当成 supabase**：[config.go L176-L182](file:///Users/qpy/Desktop/github/my_go_study/common/config/config.go#L176-L182) 只有显式 `local` 才走本地，其余一律 supabase。config.prod.yaml 没有 provider 键，所以生产若要本地 Auth 必须显式注入 `AUTH_PROVIDER`；按仓库现状（Cloud 账号体系）prod 默认对接 Supabase Cloud。
2. **WS URL 的协议被写死成 `ws://`**：`WSURL` 固定 `fmt.Sprintf("ws://%s:%d%s", ...)`（[config.go L525-L536](file:///Users/qpy/Desktop/github/my_go_study/common/config/config.go#L525-L536)），host 为空才回退 127.0.0.1。生产上 wss/TLS 网关目前⚠️ 无对应代码分支（lan 文档也把 wss 列为附录预留）；即便注入了正式 `REALTIME_PUBLIC_WS_HOST`，ticket 里仍是 `ws://`。

## 5. 多客户端接入差异（重点章节）

通俗理解：后端换场地后，要给每个客户端发一张「新地址纸条」。这张纸条在 Go 侧叫 `REALTIME_PUBLIC_WS_HOST`，在客户端侧叫 `BACKEND_HOST`；[sync-lan-ip.sh](file:///Users/qpy/Desktop/github/my_go_study/scripts/sync-lan-ip.sh) 就是统一发纸条的人。

### 5.1 两个 HOST 的本质区别

| 变量 | 所属仓库 | 消费者 | 作用 |
|---|---|---|---|
| `REALTIME_PUBLIC_WS_HOST` | Go my_go_study（`.env.lan`） | BindEnv 到 `realtime.public_ws_host`（[config.go L676](file:///Users/qpy/Desktop/github/my_go_study/common/config/config.go#L676)） | 后端签 WS ticket 时拼进 `wsUrl`（[config.go L525-L536](file:///Users/qpy/Desktop/github/my_go_study/common/config/config.go#L525-L536)），告诉客户端「WebSocket 连这个主机」 |
| `BACKEND_HOST` | 各客户端（`.env.lan`，编译期注入） | Flutter 的 `String.fromEnvironment('BACKEND_HOST')`（[backend_http_config.dart L13-L15](file:///Users/qpy/Desktop/github/my_ai_project/commons/network/lib/http/backend_http_config.dart#L13-L15)） | 客户端把默认 `127.0.0.1:8080` 的 HTTP baseUrl 改写成 Mac 局域网 IP |

二者必须是**同一个 IP**：HTTP 用 BACKEND_HOST 打 8080，登录后换票，WS 按 ticket 里的 REALTIME_PUBLIC_WS_HOST 连回同一主机的 8080（见 [09-Realtime与WebSocket](09-Realtime与WebSocket.md)）。「HTTP 通、WS 挂」的头号原因就是两边 IP 不一致（[lan-ops C4c](file:///Users/qpy/Desktop/github/my_go_study/docs/docker/lan-ops-abc-beginner.md)）。

### 5.2 lan-ip.clients 清单：5 个客户端与两种同步机制

清单在 [scripts/lan-ip.clients](file:///Users/qpy/Desktop/github/my_go_study/scripts/lan-ip.clients)，每行 **4 个 TAB 分隔字段**：`kind <TAB> 目录 <TAB> 文件 <TAB> 标记`（文件头 L11-L14 强调不能改成空格）。目录必须是 my_go_study 的同级 `../<名称>`，目录名即客户端 ID。

| 客户端（ID） | 语言栈 | 清单位 | kind | 目标文件 | 标记 | 默认开关 |
|---|---|---|---|---|---|---|
| my_ai_project | Flutter | L30 | `env` | `../my_ai_project` → `.env.lan` | `BACKEND_HOST` | **开启（唯一未注释行）** |
| my_kmp_project | KMP | L34 | `env` | `.env.lan` | `BACKEND_HOST` | 注释（注释提示该仓 .gitignore 未忽略 .env.lan） |
| my_kmp_project | KMP | L36 | `quote` | `core/network/.../LanHost.kt` | `const val fallback: String = "` | 注释（改写已入 git 源码，非必要别开） |
| my_rn_project | React Native | L39-L40 | `env` + `quote` | `.env.lan`；`packages/core/config/src/lanHost.ts`（`export const fallback = '`） | BACKEND_HOST / 单引号 | 均注释 |
| kmp_kuikly | Kuikly+KMP | L44-L45 | `env` + `quote` | `.env.lan`；`feature-home/.../pages/LanHost.kt`（`const val fallback: String = "`） | BACKEND_HOST / 双引号 | 均注释（清单注释 L43 说明其 LanHost.kt 当前不存在，quote 行会自动跳过） |
| uni_ai_project | uni-app | L48-L49 | `env` + `quote` | `.env.lan`；`src/lan-host.ts`（`export const fallback = '`） | BACKEND_HOST / 单引号 | 均注释 |

**kind=env 的写入机制**（Python L105-L124）：

1. 目标文件不存在：优先复制该客户端仓的 `.env.lan.example`；连 example 都没有就自建 stub（`# 由 sync-lan-ip 维护，勿手填固定 IP\nBACKEND_HOST=\n`）；
2. 用正则 `^MARKER=(.*)$` 找首行，找到就替换整行，找不到就追加；
3. 文件不存在于 env 规则里是「自愈」，不会失败。

**kind=quote 的写入机制**（L125-L139）：

1. 标记必须以 `'` 或 `"` 结尾，否则 `SystemExit`；
2. 正则为「标记 + 任意非引号字符 + 同引号」，**替换且仅替换 1 处**；匹配数不为 1 直接 `SystemExit` 终止整个同步；
3. 文件不存在只打印「跳过（文件不存在）」。文件头 L20-L22 明确不鼓励 quote：IP 一旦进 git 历史会被队友反复覆盖。

**跳过逻辑汇总**：空行/`#` 注释行跳过；客户端目录不存在打印「跳过（目录不存在）」继续（当前本机 my_rn_project、uni_ai_project 目录不存在，落在此分支）；`LAN_CLIENTS=a,b` 一次性覆盖时，默认客户端 my_ai_project 始终并入允许集，`LAN_CLIENTS=all` 表示清单内全部未注释行（L76-L98）；不传 LAN_CLIENTS 则按清单注释开关同步。

```text
│   └─ 不想用 Docker → make deps-up（PG+Redis）
│                      → 需要队列再起 rabbitmq 容器 → make run（+ make run-worker）
│
├─ 要用 iPhone/Android/鸿蒙真机，同一 Wi‑Fi 联调
│   ├─ 有 Docker Desktop → cp .env.lan.example .env.lan → make lan-up（全栈+观测）
│   └─ 没有 Docker / 频繁改 Go → make deps-up → make lan-run（+ make lan-run-worker）
│   两种都会先 sync-lan-ip，把 IP 写进 Go .env.lan 和客户端 .env.lan
│
├─ 真机只改 Flutter 不动 Go → 后端保持 lan-up/lan-run，客户端 run_app.sh --lan（别重建镜像）
│
├─ 要演示/验证整点广播 → dev/lan 下 make trigger-hourly-notify（prod 才自动 cron）
│
└─ 正式部署 → 构建 Dockerfile 镜像 → APP_ENV=prod + 注入 JWT_SECRET/DB/SUPABASE_*
                 → /app/api 与 /app/worker 各一份 → 反代/TLS 在镜像外解决（wss 尚待支持）
```

## 7. 模式切换检查清单

**dev → lan（真机联调）**

1. `.env.lan` 已从 example 复制，`REALTIME_PUBLIC_WS_HOST` 不是 `YOUR_LAN_IP`（脚本会自动刷，仍建议人工确认）；
2. 先停掉占用 8080 的 `make run` / `make docker-up`（文档明确二者勿同时开）；
3. 客户端 `.env.lan` 的 `BACKEND_HOST` 与 Go 同 IP（看 sync 输出有无「跳过（目录不存在）」）；
4. `curl http://<LAN_IP>:8080/health` 手机 Safari 也通；
5. 多端同账号测试：白名单邮箱写进 Go `.env.lan`。

**lan → dev（回本机/模拟器）**

1. `make lan-down`（或 Ctrl+C 停 lan-run）；
2. Flutter 改回 `.env` / 模拟器启动配置，去掉 BACKEND_HOST；
3. 注意 dev 的 Auth 回到 Supabase Cloud，短信测试号在 dev YAML 内置、lan 需显式开启。

**lan 容器 ↔ lan-run 互换**

- 两者共用同一份 `.env.lan` 与 config.lan.yaml，区别仅是依赖供给与进程形态；
- 切换时确认 5432/6379 没有两套依赖同时占用（Homebrew 与容器只能活一个绑定）；
- lan-run 需要 RabbitMQ 时，保留容器跑 rabbitmq 是可行组合（API 进程本机、MQ 在容器）。

**→ prod**

1. 替换 `JWT_SECRET`、数据库密码；确认 `database.sslmode=require` 可达；
2. 显式确认 Auth provider 策略（空值=supabase）；
3. `REALTIME_PUBLIC_WS_HOST` 换成正式主机前先评估 `ws://` 写死问题；
4. worker 用同镜像独立部署；整点广播开启后确认 cron 文案与时区（config.yaml 默认 Asia/Shanghai）；
5. 观测、反代、TLS 全部在镜像外另行搭建。

## 学习要点回顾

1. 「三端」不是三套代码：装配流程始终是 [03 篇](03-启动流程与依赖注入.md)的 15 个阶段，模式差异 = APP_ENV 选哪份 YAML + env 注入什么值 + 依赖由谁提供。
2. 三条启动链路都先 source env 再干活：`load-env.sh`（3 个文件）、`lan-compose.sh`/`lan-run.sh`（4 个文件，`.env.lan` 最后 source、优先级最高）。
3. 端口安全是显式设计：基础 compose 所有依赖一律 `127.0.0.1:` 前缀，只有 app 的 8080/9090 默认发布 0.0.0.0；Go 进程本身永远监听 `:port`，能否被外网连取决于配置姿态与端口映射。
4. 容器内走服务名（postgres/redis/rabbitmq），本机走 localhost；同一份代码靠 BindEnv 在两种寻址间切换。
5. 改 Go 代码的生效方式随模式变化：`go run` 重跑 → lan-up 必须 `--build` → prod 发新镜像；worker 与 api 同镜像、只换 command，且 worker 必须关闭 HTTP healthcheck。
6. `REALTIME_PUBLIC_WS_HOST`（后端 ticket）与 `BACKEND_HOST`（客户端 HTTP）必须是同一 IP；sync-lan-ip 用一份 TAB 清单同时维护 Go 与 5 个客户端，`env` 行自愈、`quote` 行匹配不到会硬失败。
7. dev 默认 Cloud Auth、lan 强制 local Auth、prod 的空 provider 仍会被归一化成 supabase——认证分叉由 [config.go 的 ProviderName](file:///Users/qpy/Desktop/github/my_go_study/common/config/config.go#L175-L183) 一个函数决定。
8. prod 目前有两个代码层面的未竟事项：WS 协议写死 `ws://`、观测/TLS 完全外置。
