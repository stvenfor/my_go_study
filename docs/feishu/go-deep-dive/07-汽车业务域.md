# 07 · 汽车业务域：交易流水、二手车、新车跟进、购车计算器、成交发票

> 一句话定位：五个直接服务 4S 店业务的垂直切片——transaction（Flutter 二手车 App 沿用的收支流水，三套存储实现并存）、used_car（置换/专卖/收车业务单）、new_car_follow（新车销售跟进档案与跟进流水）、purchase_calculator（全款/贷款报价，全仓唯一公开无鉴权域）、deal_invoice（新车成交发票审核）。所属模块：app 模块 `app/internal/<域>/`。阅读前置：第 04 篇的 SessionAuth 双认证、第 06 篇 access 域的「当前门店 + 权限」机制。

## 本篇怎么读

通俗理解：这是销售顾问手机里的五块业务。`transaction` 是他个人的收支记账本（Flutter 老 App 的遗留接口，跟门店业务无关，所以不看 current_store）；`used_car` 是二手车三张单子（置换/专卖/收车）；`new_car_follow` 是新车客户跟进 CRM（档案 + 跟进流水）；`purchase_calculator` 是给客户算全款/贷款落地价的计算器；`deal_invoice` 是新车成交后上传发票等审核的流程。

| 域 | 包路径 | 五件套 | 自有表 / DDL 来源 |
| --- | --- | --- | --- |
| transaction | `app/internal/transaction/` | router/handler/service/repository + repo_postgres + repo_supabase + repo_es | transactions（DDL 在 scripts/navicat_local_schema.sql + main.go AutoMigrate） |
| used_car | `app/internal/used_car/` | 五件套（+ service_test） | wys_used_car_order（仅 AutoMigrate，无 sql 文件） |
| new_car_follow | `app/internal/new_car_follow/` | 五件套 | wys_new_car_follow_file、wys_new_car_follow_log（sql/new_car_follow_schema.sql） |
| purchase_calculator | `app/internal/purchase_calculator/` | 五件套 | wys_auto_finance_product（仅 AutoMigrate） |
| deal_invoice | `app/internal/deal_invoice/` | 五件套 | wys_deal_invoice（AutoMigrate）+ wys_store_customer.phone 补列 |

两个结构性特点先记住：

1. 除 transaction 和 purchase_calculator 外，三个域都是同一个模具——Summary 四格统计 + 客户选择器（wys_store_customer）+ 列表分页 + 详情归属校验 + 创建/重提；全部用 access.Service 的 `RequireCurrentStore` 拿当前店，用 shared 的分页/状态白名单/图片归一/路径 id 工具。
2. 装配按认证提供方分流（[main.go](file:///Users/qpy/Desktop/github/my_go_study/app/cmd/api/main.go#L168-L293)）：local provider 走本地 Postgres 实现并跑各域 EnsureSchema/EnsureSeed；Supabase provider 只挂 transaction 的 Supabase 实现；ES 存储仅在 `cfg.Elasticsearch.Enabled()` 时额外挂载。

# 一、transaction 域：收支流水与三套存储实现

源码锚点：[app/internal/transaction/](file:///Users/qpy/Desktop/github/my_go_study/app/internal/transaction)。

通俗理解：这个域是「个人记账本」CRUD，**不属于门店业务**——不读 current_store、不校验权限码，只按会话 user_id 隔离。它最有学习价值的地方是同一个 `Repository` 接口有两个云端实现（本机 Postgres / Supabase PostgREST），外加一个只实现 `SearchStore` 接口的 ES 索引，且必须同时兼容 Flutter 老 App 的 legacy 响应格式和新的统一响应格式。

## 1.2 Repository 接口与三实现方法表

源码锚点：[repository.go](file:///Users/qpy/Desktop/github/my_go_study/app/internal/transaction/repository.go)，定义两个接口：

| 接口 | 方法 |
| --- | --- |
| `Repository` | List、ListPage（多返 total）、GetByID、Create、Update、Delete —— 签名全部带 `accessToken, userID string` |
| `SearchStore`（可选） | Index、Delete、Search(ctx, userID, q, limit) |

### PostgresRepository（[repo_postgres.go](file:///Users/qpy/Desktop/github/my_go_study/app/internal/transaction/repo_postgres.go)）

`NewPostgresRepository(db) Repository`，local provider 装配。

| 方法 | 行为要点 |
| --- | --- |
| `ListPage` | accessToken 形参用 `_` 丢弃；`requireUUID` 其实只做 trim + 非空校验（名字叫 UUID 但不解析格式）；GORM where user_id + 可选 type；先 COUNT；limit<=0 默认 50、offset<0 归 0；排序 `date DESC, id DESC` |
| `List` | 直接调 ListPage 丢弃 total |
| `GetByID` | `id AND user_id` 双条件 First；未找到返回 `fmt.Errorf("交易记录不存在")`（普通 error，非哨兵） |
| `Create` | user_id 复制为局部指针写入；created_at/updated_at 写 UTC now |
| `Update` | 先查归属行→只对非 nil 指针字段组 map Updates→updated_at=now→重新 First 刷新；空更新直接返回原行 |
| `Delete` | 双条件物理删除；RowsAffected==0 返回「交易记录不存在」 |

### SupabaseRepository（[repo_supabase.go](file:///Users/qpy/Desktop/github/my_go_study/app/internal/transaction/repo_supabase.go)）

`NewSupabaseRepository(client *pkgsb.Client)`，Supabase provider 装配。每个方法第一步 `r.client.WithUserToken(accessToken)`——用**登录用户 JWT** 调 PostgREST，靠 RLS 的 auth.uid() 过滤，注释明确禁止 service_role 替代。

| 方法 | 与 Postgres 版的差异 |
| --- | --- |
| `List` | query builder：From→Select("*")→Eq user_id（RLS 之外的双保险）→Order date desc→Limit；offset>0 时 Range；**不返回 total** |
| `ListPage` | Select 第二参传 `"exact"` 触发 Prefer: count=exact，Execute 返回 total；limit<=0 默认 20 |
| `GetByID` | Eq id（字符串化）+ Eq user_id + `.Single()`；返回体经包内泛型 `unmarshalSingle[T]` 兼容对象/单元素数组 |
| `Create` | payload 里 **user_id 由服务端强制赋值**（注释：不信任客户端 body）；时间戳格式 RFC3339 字符串；Insert + representation + Single |
| `Update` | 只放非 nil 字段 + updated_at；Update 带双 Eq 限定 |
| `Delete` | 双 Eq，无 RowsAffected 反馈，删不存在的行不报错 |

`unmarshalSingle` 是切片时从旧 supabase 包搬来的副本（文件注释说明 profile 域也曾共用，待批 4 再上提 shared）。

### ESStore（[repo_es.go](file:///Users/qpy/Desktop/github/my_go_study/app/internal/transaction/repo_es.go)）

不引官方 ES client，纯 net/http（5 秒超时），索引名常量 `TransactionsIndex = "transactions"`（与 PG 表同名但是两个系统）。

| 方法 | HTTP / 查询要点 |
| --- | --- |
| `NewESStore(baseURL)` | 去尾斜杠 |
| `EnsureIndex` | PUT /transactions 建 mapping：id long、user_id keyword、type/category text+keyword 子字段、note text、amount double、date keyword；400 且含 resource_already_exists 视为成功 |
| `Index` | PUT /transactions/_doc/{id} 全量覆盖，文档 7 字段（不索引时间戳） |
| `Delete` | DELETE 同路径，404 视为成功 |
| `Search` | POST /_search：恒有 `term user_id` filter；q 非空加 `multi_match`（fields=note/category/type）；size 默认 20、封顶 100；sort id desc；手工解析 hits._source 重建实体（时间戳留空） |

### 三实现对比速查

| 维度 | PostgresRepository | SupabaseRepository | ESStore |
| --- | --- | --- | --- |
| 角色 | 主存储（local） | 主存储（线上 Flutter） | 只做搜索索引，可选 |
| 实现接口 | Repository | Repository | SearchStore |
| 凭据 | 连接池（服务端身份） | 透传用户 JWT，RLS 鉴权 | 无鉴权，内网 baseURL |
| accessToken | 丢弃 | 每次必用 | 不涉及 |
| 隔离 | WHERE user_id | RLS + Eq user_id 双保险 | term filter user_id |
| total 计数 | COUNT | Prefer count=exact | 无（hits 即页） |
| 错误风格 | 中文 fmt.Errorf 包装 | 中文 fmt.Errorf 包装 PostgREST 错 | HTTP 状态 + 截断 200 字节响应体 |
| 一致性关系 | 权威写库 | 权威写库（二选一装配） | 从库：best-effort 同步，无 outbox |

## 1.6 请求链路（创建并索引）

1. `POST /transactions/manage` → SessionAuth 写入身份。
2. handler 取 accessToken + user.ID，绑 DTO，调 Service.Create。
3. local 分支：PostgresRepository INSERT 本地表；supabase 分支：携用户 JWT POST PostgREST（RLS 校验），user_id 服务端覆盖。
4. Service 若挂了 ES：PUT /transactions/_doc/{id}；失败仅 metrics+1、Warn 日志，接口照常 201。
5. 之后 `GET /transactions/search?q=...` 查 ES；ES 未挂时 503。

## 1.7 假实现边界与种子

- ES 是**最终一致的从索引且无补偿**：写库后索引失败不会重试（代码注释已列为技术债，升级方向事务 outbox / 异步补偿）；索引数据也可能因历史数据缺失而搜不到。
- 事务域无 EnsureSeed（仅 import-supabase / navicat 脚本侧有数据来源）。
- legacy 与 manage 两套响应壳并存，不做格式统一；`List` 用 query 里有没有 page 区分，是典型的路由兼容 hack。
- `requireUUID` 名校实不符：不做 UUID 格式校验，只挡空串。

- 同样没有审核端/评价端接口；状态 1/2/3 与 reject_reason、rating_stars 对销售端是只读种子数据。
- resubmit 是全字段 Save（并发无版本号/条件更新，后写覆盖）。
- [EnsureSeed](file:///Users/qpy/Desktop/github/my_go_study/app/internal/deal_invoice/repo_postgres.go#L145-L259) 针对测试号：店内 0 客户时造 3 个带手机号客户；已有客户缺手机号的按序回填 13812345678/13612345678/13987654321 并补空姓名；本人无发票时造 5 张（已评价5星-96h、待评价-72h、待审-48h、待审-24h、驳回「发票信息不清晰，请重新上传」-12h），全部挂第一个客户。

# 学习要点回顾

1. 同接口多实现的选择发生在**装配层而非业务层**：transaction.Service 不知道背后是 GORM 还是 PostgREST；凭据模型（服务端连接 vs 用户 JWT+RLS）是实现差异的根因。
2. 读多存储代码先比对三件事：身份如何传递、隔离在哪一层执行、分页 total 怎么来——这三点正好构成本篇三实现对比表的骨架。
3. 「同模具域」的识别：Summary/List/Get/Create + 客户选择器 + 四格统计 + 双归属校验，在 used_car、deal_invoice 重复出现，差异只在实体字段与状态动作（resubmit）。
4. 状态机的暴露面要和接口对齐：审核四态在销售端只有「提交」和（驳回后）「重提」两个写动作，其余状态靠外部系统推进——不要把字段存在等同于能力存在。
5. CRM 模型的两个事务技巧：多表联动一个事务（流水+档案+客户跟进时间），以及用 TouchXxx 布尔位区分「字段未传」与「显式清空」（PATCH 的 null 语义）。
6. 唯一约束防重与先查后插防重的可靠性差别：new_car_follow 的 open 档案防重只在 service 层，高并发下有口子；读代码时要找数据库约束作为最后防线。
7. 公开域的代价：purchase_calculator 无鉴权、无留痕，金融政策对全网可见——暴露无敏感数据的纯计算是合理取舍，但要意识到它不是默认形态。
8. best-effort 旁路索引必须显式声明降级语义（metrics + 日志 + 不回滚），否则搜索与主库不一致会变成隐性 bug。
