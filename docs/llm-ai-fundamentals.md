# AI 基础概念详解：从「听懂话」到「能干活」

本文用通俗说法说明大模型相关基础概念，分两层：

1. **基础层**：模型怎么理解你说的话  
2. **能力层**：模型怎么真正办事（查资料、调工具）

适合作为日常查阅笔记，不要求有机器学习背景。

---

## 一张总览图

```text
你说话 / 写需求
        │
        ▼
┌─────────────────────────── 基础层 ───────────────────────────┐
│  Prompt（你说的话）                                          │
│       → Token（拆成小块）                                    │
│       → Context（带上历史/相关材料）                         │
│       → LLM（猜下一个该接什么）                              │
│       → Memory（太长时压缩旧对话）                           │
└──────────────────────────────────────────────────────────────┘
        │
        ▼  仅靠「猜字」不够时，加上能力层
┌─────────────────────────── 能力层 ───────────────────────────┐
│  RAG：先检索私有资料，再生成                                 │
│  Function Calling：模型下指令 → 程序调工具 → 结果回传        │
│  MCP：第三方工具用统一协议接入（挂工具的标准插座）           │
└──────────────────────────────────────────────────────────────┘
```

---

## 一、基础层：模型怎么理解你说的话

### 1. LLM（大语言模型）

**一句话**：核心引擎——读你输入的文字，不断预测「下一个最该接什么」，连成整段回答。

可以把它想成一个「超级自动补全」：

- 输入：前面已经出现的文字  
- 输出：下一个最可能出现的片段  
- 重复很多次：就变成完整回复、代码、总结……

它**不会**像人一样真正「理解」世界，而是根据训练时见过的海量文本，学会了语言的统计规律。所以：

- 问得清楚 → 更容易落到正确路径  
- 资料不足或过时 → 可能一本正经地编（幻觉）

常见产品（ChatGPT、Claude、Cursor 里的 Agent 等）背后都是这类模型，再套上对话界面、工具、检索等能力。

---

### 2. Token（词元）

**一句话**：模型理解文字的最小单元；每个 token 对应一个数字 ID。

模型并不直接「看汉字/英文单词」，而是先把文本切成小块：

| 例子 | 大致情况（示意） |
|------|------------------|
| 英文 `hello` | 可能是 1 个 token |
| 中文「你好」 | 可能是 1～2 个 token |
| 一段长代码 | 往往会拆成很多 token |

每个 token 映射成数字后，模型才能做计算。你需要记住的实用点：

- **按 token 计费、限长**，不是严格按「字数」  
- 中文通常比同样含义的英文更「吃」token  
- 上下文窗口 = 一次请求里能塞进的 token 上限（含你的问题、历史、系统提示、检索到的资料、模型回复等）

---

### 3. Prompt（提示词）

**一句话**：你对模型说的话——问题、指令、背景、约束，都算 Prompt。

广义上，一次请求里给模型的文本都可以叫 Prompt，例如：

- 「用三句话解释 Redis 是干什么的」  
- 「你是资深 Go 审查员，只指出缺陷……」  
- 系统预设的角色说明 + 你的当前问题

Prompt 质量直接影响输出质量：**模型很强，但读心术有限**。你没说的约束，它往往会自己猜。

---

### 4. Prompt Engineering（提示词工程）

**一句话**：把话说清楚的方法论——问得越好，答得越稳。

不是玄学，而是可重复的写法习惯。常用技巧：

| 技巧 | 做什么 | 例子 |
|------|--------|------|
| 明确目标 | 说明要产出什么 | 「写一页飞书可读的说明，不要代码」 |
| 给约束 | 范围、格式、语气 | 「用表格；每条不超过两句」 |
| 给上下文 | 背景、读者是谁 | 「面向没学过 ML 的后端同学」 |
| 给示例 | Few-shot | 先给 1～2 个好坏示例 |
| 分步 | 复杂任务拆开 | 「先列大纲，我确认后再展开」 |
| 要求自检 | 减少遗漏 | 「回复前核对是否覆盖了 RAG / MCP」 |

经验法则：**把你对实习生会交代清楚的信息，写进 Prompt**。

---

### 5. Context（上下文）

**一句话**：每次发消息时，系统把「当前问题 + 相关历史/材料」打包发给模型。

重要事实：

- 模型**默认不记得**你上周的聊天（除非产品层帮你存、再塞回来）  
- 每一次调用，本质上都是：「拿这一包 Context，生成续写」  
- 对话产品会自动把最近若干轮拼进 Context；Agent 还可能塞进打开的文件、检索结果、工具返回值

所以「它怎么知道我刚才说过什么」——答案通常是：**被放进了这次的 Context**，不是大脑里有长期记忆。

---

### 6. Memory（记忆）

**一句话**：上下文窗口有限；产品会把旧对话压缩成关键信息再带上，相当于「记重点，不记全文」。

和 Context 的关系：

```text
完整历史对话可能很长
        │
        ▼
装得下 → 直接放进 Context
装不下 → Memory / 摘要 / 向量库检索「相关片段」再放进 Context
```

常见形态：

- **会话内摘要**：把前 50 轮压成一段「用户偏好与结论」  
- **长期记忆**：跨会话保存「我叫小明、偏好简体中文」之类  
- **工作区记忆**：记住当前仓库约定（例如本仓库的 `AGENTS.md`）

注意：压缩会丢细节。重要约束应写进稳定文档或每次关键 Prompt，不要只依赖「它应该记得」。

---

### 基础层小结

| 概念 | 角色 |
|------|------|
| LLM | 引擎：按 token 预测下文 |
| Token | 文字的最小计算单位 |
| Prompt | 你输入的指令与问题 |
| Prompt Engineering | 把指令写清楚的方法 |
| Context | 本次请求打包给模型的全部材料 |
| Memory | 窗口不够时，对历史的压缩与再注入 |

**串起来**：你说话 → 拆成 Token → 连同 Context（及 Memory 精华）进 LLM → 按 Prompt 生成回复。

## 二、能力层：模型怎么真正干活

仅有「猜下一个 token」只能聊天。要查公司文档、改数据库、调 API，需要能力层。

### 1. RAG（检索增强生成）

**一句话**：让模型先读你的私有资料，再回答——先检索相关片段，拼进上下文，再生成。

#### 为什么需要

LLM 训练数据不含你的内部 Wiki、未公开接口、最新业务规则。直接问容易：

- 编造不存在的接口  
- 用过时的公开知识瞎猜  

RAG 的思路是：**把「该知道的段落」临时塞进 Context**，再让模型基于这些段落回答。

#### 典型流程

```text
1. 准备：把文档切片 → 做成可检索的知识库（常配合向量索引）
2. 提问：用问题去知识库找「最相关的几段」
3. 增强：把片段 + 原问题一起放进 Prompt / Context
4. 生成：模型根据这些片段写答案（并可要求标注来源）
```

#### 和生活类比

开卷考试：允许翻指定参考书相关页，再答题——不是把整座图书馆背下来。

#### 适用与局限

| 适合 | 不太适合单独靠 RAG |
|------|---------------------|
| 制度、手册、设计文档问答 | 需要实时写操作（下单、改配置） |
| 降低幻觉、可追溯来源 | 强推理但资料里根本没有的答案 |
| 私有知识更新比「重新训练模型」便宜 | 检索质量差时仍会答偏 |

---

### 2. Function Calling（函数 / 工具调用）

**一句话**：让模型能调用外部工具——模型只输出「结构化调用指令」，由程序执行，再把结果还给模型。

模型本身通常不能真的访问你的数据库或浏览器；产品约定一组工具后：

```text
用户：帮我查一下健康检查接口是否正常
        │
        ▼
模型：我需要调用工具 get_url，参数 url=http://127.0.0.1:8080/health
        │
        ▼
程序：真正发 HTTP 请求，得到 {"status":"ok"}
        │
        ▼
模型：根据返回结果告诉用户「服务正常」
```

要点：

- **模型负责决策**：调不调、调哪个、参数是什么  
- **运行时负责执行**：鉴权、网络、副作用、安全策略  
- **结果再进入 Context**：模型据此继续推理或回复用户  

这和「让模型直接假装自己查过了」不同——中间有一次真实执行。

---

### 3. MCP（Model Context Protocol）

**一句话**：统一第三方工具 / 数据源接入方式的协议。它不是 Function Calling 的替代品。

容易混淆，可以这样区分：

| | Function Calling | MCP |
|--|------------------|-----|
| 解决什么 | **模型怎么表达「我要调工具」**（输出结构化指令） | **工具怎么被统一接入**（标准插座） |
| 类比 | 你说「请帮我叫车，去机场」 | 叫车 App 的统一接口规范 |
| 关系 | 能力层的「调用方式」 | 能力层的「接入标准」 |

没有 MCP 时，每个产品要为 GitHub、浏览器、数据库各自写一套对接。有了 MCP，工具方可按协议暴露能力，宿主（IDE、Agent 运行时）按协议发现并调用。

对使用者的体感：

- 仍会看到「模型决定调用某个工具」——那是 Function Calling（或等价机制）  
- 工具从哪来、如何鉴权与列举——往往由 MCP（或同类协议）支撑  

**二者互补，不是二选一。**

---

### 能力层小结

| 概念 | 解决的问题 |
|------|------------|
| RAG | 模型缺少你的私有 / 最新资料 |
| Function Calling | 模型需要真实执行外部动作并拿回结果 |
| MCP | 大量第三方工具如何用同一套方式接入 |

**串起来**：会查资料（RAG）+ 会下指令调工具（Function Calling）+ 工具统一接入（MCP）→ 模型从「会聊天」变成「能办事」。

---

## 三、三者如何配合（完整一问）

场景：你问 Agent——「根据我们仓库的 AGENTS.md，本地怎么验证 Realtime？」

可能的路径：

1. **Prompt / Context**：你的问题 + 系统角色说明进入请求  
2. **RAG 或直接读文件**：检索 / 打开 `AGENTS.md`、`docs/realtime-*.md` 相关段落  
3. **Function Calling**：必要时执行 `make test-realtime` 或读终端输出  
4. **LLM**：综合材料生成步骤说明  
5. 若对话很长，**Memory** 保留「用户在做 Realtime 联调」等要点，供后续轮次使用  

MCP 在此例中可能体现为：文件系统、终端、浏览器等以统一协议挂到 Agent 上，供 Function Calling 选用。
