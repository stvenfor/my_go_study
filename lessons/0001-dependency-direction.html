Lesson 0001 · 约 18 分钟 · 目标：面试表达

一条箭头

证明 core 不依赖 app，并说清「接口放在最内层」到底解决了什么。

本课只练一件事：跑完你能（1）用一条命令自己验证依赖方向，（2）用 60 秒讲清依赖倒置在本仓库长什么样。不需要你记住分层名词。

A · 先给三个事实（5 分钟）

事实 1：本仓库是 4 个 Go module，不是 4 个文件夹

go.work 里 use ./common ./core ./model ./app。模块之间是真编译边界：跨模块 import 要写完整路径（import "model/repository"），所以「谁依赖谁」是可以被命令查出来的——这是本课的立足点。

事实 2：规则只有一句，方向只能向内

Dependency Rule 源码依赖只能指向内层、指向更稳定的一侧。
《Clean Architecture》第 22 章 · InformIT 官方节选（作者本人写的版本，比转述可靠）

本仓库的落法：model / common 是叶子（谁都不依赖）→ core 依赖它们 → app 依赖全部。反向 import 是不允许的，而「不允许」这件事下面会自己去证明。

事实 3：反直觉的那一点，才是面试的得分点

请求真正跑起来时，控制流是从内往外的：handler → usecase → 接口 → Redis 实现。但源码依赖是从外向内的：app/internal/repository/redis/session_repo.go 里写的是 import "model/repository"。

记住这句 两条箭头方向相反，这个「相反」就是依赖倒置。不是命名游戏，也不是「多加一层文件夹」。

为什么做得到？因为 Go 的接口是隐式满足的：实现方不需要知道接口存在，方法集齐了就算实现（Effective Go · Interfaces）。于是接口可以留在内层，实现安心放外层。

B · 自己去证明（6 分钟）

打开终端，在 my_go_study/ 下逐条跑，把数字抄在这里：

grep -rl '"app/' core --include='*.go' | wc -l                        # 你的结果：______
grep -rl '"common/\|"core/\|"app/' model --include='*.go' | wc -l      # 你的结果：______
grep -rl '"core/\|"model/' app --include='*.go' | wc -l                # 你的结果：______

前两条必须是 0，第三条必须 > 0。不为 0 就说明有反向依赖，那才是真问题。

为什么 grep 就够（而不是必须 go list） Go 的 import 别名只改包名、不改路径字符串——本仓库 app/cmd/api/main.go:20 就是 grpcdelivery "app/internal/delivery/grpc"，别名换了但 "app/ 还在，搜不丢。grep 只会误报（注释或字符串里出现路径），不会漏报。
真要按编译器视角查传递依赖，命令是 go -C core list -deps ./... | grep '^app/'——但本机现在跑不动它：它会先解析整张模块图，网络受限时长时间无输出（go env 本身 0.015s 就返回，卡的不是 go 命令）。所以本课以 grep 为准，go list 只作为「你网络正常时再试」的深挖项。

然后对读三个文件（这是本课真正的收获）

  1. model/repository/session_repository.go —— 4 个方法的接口 + DeviceSession 结构体。注意它只 import 了 context 和 time，连 redis 这个词都没出现。
  2. app/internal/repository/redis/session_repo.go:16 —— type SessionRepository struct，同名但不同包，它 import 了 "model/repository"。
  3. app/internal/delivery/worker/handler.go:33 —— 字段类型写的是 repository.SessionRepository（接口），不是 Redis 那个实现类型。

1. 本仓库里 SessionRepository 这个接口定义在哪个模块？

  • app —— 实现与装配所在的模块
  • model —— 依赖最少的内层模块
  • core —— 封装外部系统的模块

接口在 model/repository/session_repository.go。Redis 实现才在 app。接口留在内层，外层才能依赖它而不违反方向规则。

2. Go 判断一个类型是否实现了某接口，依据是什么？

  • 结构体声明里是否写了 implements 关键字
  • 接口定义文件里是否登记了该类型名
  • 该类型方法集是否覆盖接口全部方法

Go 没有 implements：方法集齐全即隐式满足。好处是实现方不必知道接口存在，坏处是「实现了」这件事在源码里看不见——所以要下一题那个写法。

3. var _ repository.SessionRepository = (*SessionRepository)(nil) 这行做什么？

  • 运行时检查该接口是否已经被初始化
  • 编译期断言该类型确实实现了该接口
  • 启动时把实现注册进全局依赖容器

纯编译期：把 (*SessionRepository)(nil) 赋给接口类型的空变量，方法集不齐就编译失败。Go 惯用法，零运行时开销。

4. Dependency Rule 的准确表述是哪个？

  • 源码依赖只能指向内层更稳定的一侧
  • 所有函数参数都必须声明为接口类型
  • 外层框架代码不得包含任何业务判断

规则只约束源码依赖方向，不约束控制流，也不要求「到处都是接口」。后两个是把 Clean Architecture 念歪了的常见版本——面试官很爱在这里下钩子。

C · 一个真实的不一致（3 分钟）

对读时你会发现：本仓库有些仓储实现写了编译期断言，app/internal/repository/redis/realtime_event_repo.go:86 有；而 session_repo.go 没有。

想一想（不用答对，要有立场） 少了这行会怎样？答案是：接口加一个方法时，编译器不会立刻在实现文件报错，要等到这个实现被赋值给接口类型的那一刻才炸——报错位置离真正该改的地方很远。所以这行断言的价值是把错误搬回现场。反过来，它的代价是多一行噪音。你选哪边？

D · 说一遍（4 分钟，别跳过）

目标不是「看懂」，是「说得出」。打开速查页的 60 秒模板，把空填上，然后出声说一遍（对自己说，或打在聊天里让我看）。

骨架就三段：方向规则 → 一个真实类型证明它 → 我说出它的代价。第三段是区分「背过」和「想过」的地方。

卡住就问你的老师。比如：「context.Context 为什么每个方法第一个参数都是它？」「common 和 model 都是叶子，为什么不合成一个模块？」「我上一题选错了，为什么 core 不算内层？」——这些问题比顺利学完更值钱，而且都能在本仓库里找到答案。
